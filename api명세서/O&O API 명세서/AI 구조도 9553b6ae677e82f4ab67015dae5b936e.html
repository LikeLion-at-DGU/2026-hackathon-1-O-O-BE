AI 구조도

런타임에 AI를 호출하는 곳은 2곳뿐이다.
추천 순위와 캐릭터 이미지는 AI가 아니다 — 하나는 계산이고, 하나는 사전 제작 자산이다.
이 둘을 런타임에서 분리한 것이 이 설계의 핵심이다.

1. 전체 흐름

┌─ 실시간 (HTTP 연결 유지) ──────────────────────────────────┐
│                                                            │
│  POST /chat                                                │
│    visit_token → visit 확정                                │
│    ChatLog(user) 저장  ← PII 마스킹                         │
│    프롬프트 조립: 이 visit의 대화 10턴 + 매장 상품 llm_context│
│         ↓                                                  │
│    ▣ AI ①  텍스트 스트리밍                                  │
│         ↓                                                  │
│    ChatLog(assistant) 저장                                 │
│                                                            │
│    ※ 취향 해석 안 함. 저장만 한다                            │
└────────────────────────────────────────────────────────────┘
                            │
                    POST /finish
                            │
┌─ 비동기 (연결 없음, visit_id만 들고 감) ────────────────────┐
│                                                            │
│  ① 이벤트 집계          계산   <10ms                        │
│  ② 관심도 (log 가중합)   계산   <10ms                        │
│  ③ confidence           계산   <10ms                        │
│         ↓                                                  │
│  ④ ▣ AI ②  대화 전체 → JSON                3~4초           │
│           { preference_tags, avoid_tags,                   │
│             purchase_intent, report_summary }              │
│         ↓                                                  │
│  ⑤ 취향 벡터 (피처 합산 + 태그 가감점)  계산   <10ms          │
│  ⑥ 스코어링 (개인75 + 인기15 + 신상10)  계산   <10ms          │
│  ⑦ 16유형 매핑 + characters 조회       계산   <10ms          │
│         ↑ 이미지 URL은 DB 한 행에서 꾼낸다. AI 호출 아님       │
│         ↓                                                  │
│  Report(slug, payload) 저장 → status: ready                │
└────────────────────────────────────────────────────────────┘

AI가 하는 일은 "정성적 해석"뿐이다. 순위·점수·유형 판정·이미지는 전부 결정론적이다.

2. AI 사용 지점

위치종류시점호출 수
①챗봇 응답텍스트, 스트리밍실시간대화 턴 수만큼
②태그 추출 + 리포트 문구텍스트, JSON 출력워커방문당 1회
—추천 순위계산워커—
—캐릭터 이미지사전 제작 자산——

①②는 같은 모델·같은 API 키를 쓴다. 런타임 AI는 이 둘이 전부다.

캐릭터 이미지가 AI 지점이 아닌 이유

16유형은 고정이므로 이미지도 16장 고정이다. 한 번 만들어 CDN에 올려두고, 워커는 characters 테이블에서 URL을 꾼내 쓴다.

python

# ⑦단계 — AI 호출이 아니라 DB 조회

    "type_code": row.type_code, "name": row.name,

이미지를 AI로 제작하더라도 그건 한 번 하고 끝나는 작업이라 시스템 구조에 등장하지 않는다. 디자이너가 그려도 구조는 동일하다.

사전 제작 16장방문마다 생성
워커 지연0수 초
비용1회방문 수 비례
실패 처리불필요태스크 분리 + 폴백 필요
API 계약필드 추가만폴링 규약 변경
품질검수 완료본매번 다름

characters 테이블은 16행 마스터다. 이미지·문구를 바꿀 때 배포가 필요 없다 — DB 한 행만 고치면 다음 리포트부터 반영된다.

3. AI ① — 챗봇

컨텍스트 조립

python

# apps/chat/context.py
def build(visit, message, context=None) -> Prompt:
    history = ChatLog.objects.for_visit(visit).order_by("-created_at")[:10]

    focus = None
    if context and context.get("product_id"):
        # 다른 매장 상품 주입을 막는다
        focus = Product.objects.filter(
            id=context["product_id"], scene__store=visit.store
        ).first()

    return Prompt(
        system=SYSTEM_PROMPT,
        store=visit.store,
        focus=focus,                                   # 지금 보고 있는 상품
        catalog=[p.llm_context for p in store_products(visit.store)],
        history=reversed(history),
        user_message=message,
    )

focus가 있어야 "이거 소재가 뭐야?"의 "이거" 를 해석할 수 있다. 팀 명세서의 context: { scene_id, product_id } 필드가 이것이다.

SYSTEM_PROMPT = """

- 재고, 할인, 입고 예정은 알 수 없습니다. 확정적으로 답하지 마세요.
- 가격은 제공된 값만 말하고, 추정하지 마세요.
- 답변은 2~3문장으로 짧게. 대화하듯이.

하지 말아야 할 것
- 상품 정보에 없는 소재·원산지·사이즈를 지어내기

프롬프트보다 데이터로 막는 게 강하다. llm_context에 재고·할인 필드를 애초에 넣지 않으면, 모델이 지어낼 재료조차 없다. 프롬프트 지시는 확률적으로 새지만 데이터 부재는 구조적이다.

스트리밍

python

def respond(visit, message, context=None):
    ChatLog.objects.create(visit=visit, role="user",
                           content=privacy.mask_pii(message))   # ① 먼저 저장

    prompt = build(visit, message, context)
    chunks = []
    completed = False
    try:
        for chunk in llm.stream(prompt):
            chunks.append(chunk)
            yield chunk
        completed = True
    finally:
        if chunks:
            ChatLog.objects.create(visit=visit, role="assistant",
                                   content="".join(chunks),
                                   is_partial=not completed)

질문을 먼저 저장하는 이유는 스트리밍이 끊겨도 질문이 남게 하기 위해서다. 질문은 그 자체로 취향 신호라 답변보다 분석 가치가 높다.

SSE 응답 규약

data: {"delta": "이 제품은 "}
data: {"delta": "코팅 캔버스 소재입니다."}
data: {"done": true, "message_id": "m_55"}

스트림 시작 후에는 HTTP 에러 코드를 쓸 수 없다. 에러도 스트림 안에서 알린다.

data: {"error": {"code": "LLM_TIMEOUT"}}
data: {"done": true, "message_id": "m_55", "is_partial": true}

400/401/429는 스트림 시작 전에만 유효하다.

5. AI를 쓰지 않는 곳 — 추천 순위

python

# apps/analysis/scoring.py
WEIGHT_PERSONAL = 0.75
WEIGHT_POPULAR  = 0.15
WEIGHT_NEW      = 0.10
BONUS_UNSEEN    = 0.05

def score(vector, market) -> list[ScoredProduct]:
    out = []
    for p in market.products:
        personal = cosine(vector, p.feature_vector)
        s = (WEIGHT_PERSONAL * personal
             + WEIGHT_POPULAR * market.popularity[p.id]
             + WEIGHT_NEW * p.newness)
        if p.id not in vector.seen_ids:
            s += BONUS_UNSEEN
        out.append(ScoredProduct(p, s, breakdown={
            "personal": personal, "popular": market.popularity[p.id],
            "new": p.newness,
        }))
    return sorted(out, key=lambda x: -x.score)

왜 LLM에 맡기면 안 되나

문제결과
재현성 없음같은 링크를 다시 열면 순위가 달라짐 → "박제" 위반
할루시네이션존재하지 않는 상품 추천 → 명품 매장에서 즉시 사고
설명 불가브랜드가 "왜 1위죠?"라고 물으면 답할 수 없음
튜닝 불가가중치 조정 효과를 측정할 수 없음

리포트의 recommendations[].reason이 결정적이다.

json

{ "product_id": "p_204", "reason": "선호 소재(레더) 일치", "score": 0.87 }

이 reason은 breakdown에서 기계적으로 생성한다. 어느 항목이 점수를 가장 많이 올렸는지 보면 이유가 나온다.

python

def explain(scored) -> str:
    top = max(scored.breakdown, key=scored.breakdown.get)
    return REASON_TEMPLATES[top].format(...)

LLM에 순위를 맡기면 이 근거를 만들어낼 수 없다. B2B 데이터가 제품인 회사에서 설명 불가능한 추천은 팔 수 없다.

16유형 매핑도 계산이다

python

def map_character(axis_scores) -> Character:
    code = "".join(
        axis.high if axis_scores[axis.name] >= 0.5 else axis.low
        for axis in AXES
    )
    return CHARACTERS[code]        # 16개 사전 정의

4축 × 2값 = 16유형. CLBM 같은 코드가 나온다.
축 정의(무엇이 C이고 무엇이 T인가)는 기획이 확정해야 하며, 코드는 그 표를 그대로 옮기기만 한다.

6. 격리

벤더에 상태를 남기지 않는다

python

# ✗ 대화 세션/스레드 기능 — 상태가 우리 DB 밖에 생긴다
thread = client.threads.create()

# ✓ 매번 우리가 조립해서 보낸다

세션 기능을 쓰면 thread_id ↔ visit 매핑을 따로 관리해야 하고, 구분 책임이 우리 손을 떠난다. 명세서의 "서버 메모리에 상태 안 둠"과도 어긋난다.

API는 stateless라 같은 키를 전 방문자가 공유해도 섞이지 않는다. 구분은 전적으로 visit_token → visit → DB 필터가 한다.

이미지 경로에는 개인 데이터가 흐르지 않는다

사전 제작 방식이라 런타임에 이미지 벤더로 나가는 데이터가 아예 없다. 워커는 DB에서 URL을 읽을 뿐이다. 나중에 "방문마다 다른 이미지"로 방향이 바뀜면 그때 이 경계를 만들어야 한다.

python

# ✗ 개인 발화가 외부로
imagegen.create(prompt=f"{chat_history} 바탕으로 캐릭터를 그려줘")

# ✓ 유형 코드 + 태그만
imagegen.create(character_code="CLBM", tags=["black", "structured"])

imagegen의 입력 타입을 CharacterCode + list[Tag]로 못 박으면 원문이 들어갈 자리가 없어진다.

프롬프트에 타인 발화를 넣지 않는다

"다른 방문자들이 많이 묻는 질문"을 컨텍스트에 넣고 싶어지는 순간이 온다. 집계된 수치는 되고, 발화 원문은 안 된다.

10. 비용 구조

방문 1건당 호출 수:

챗봇      대화 턴 수 (0~20, 대화 안 하는 방문이 다수)
워커      1회 (대화 있으면), 0회 (대화 없으면)
이미지    0회 — 런타임 호출 없음 (16장 사전 제작, DB 조회만)

비용의 대부분이 챗봇에서 나온다. 줄이려면:

  • 히스토리를 10턴으로 제한 (이미 적용)
  • catalog를 전 상품이 아니라 현재 씬 + focus 상품으로 좁히기
  • 상품 llm_context를 짧게 유지 (200자 내외)

컨텍스트 길이가 비용에 직결되므로, llm_context를 장황하게 쓰면 매 턴 비용이 늘어난다.

구체적 단가는 모델 선정 시점에 확인이 필요하다.
