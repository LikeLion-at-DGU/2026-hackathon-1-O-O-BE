장고 구조

Django 프로젝트 구조

모듈 지도(MODULE_MAP.md)를 Django app으로 옮긴 것.
모듈과 app이 1:1이 아니다. 매핑 규칙을 먼저 정리한다.

1. 모듈 → app 매핑

Django app의 본질은 모델을 소유하는 단위다. 우리 모듈 중 일부는 모델이 없고, 반대로 한 app에 여러 모듈이 들어간다.

모듈app비고
identityapps.visitsVisitor가 Visit과 항상 함께 쓰여 app을 합침
visitsapps.visits1:1
stores.repositoryapps.catalog3개 모듈이 한 app
stores.catalogapps.catalog구 map_query. 좌표가 빠지며 축소
stores.market_statsapps.catalog
eventsapps.events1:1
chatapps.chat1:1
analysisapps.analysis1:1
reportsapps.analysis모델을 소유하지 않음. Report는 analysis 것
adminapps.dashboard모델 없음. 이름 충돌 회피 (아래 8장)
llm / privacycommon/app 아님. 순수 파이썬 패키지

imagegen 모듈은 두지 않는다. 캐릭터 이미지가 사전 제작 16장이라 런타임 생성 코드가 없다.

조합 서비스는 어디에 두나

EnterService는 4개 app을 조합한다. 어느 app에도 속하지 않으므로 api/ 패키지에 둔다.

api/v1/enter/services.py     ← identity + visits + stores 조합

app 안에 두면 "왜 visits가 catalog를 import하지?"가 되어 의존 규칙이 무너진다. api/는 최상위라 아래 모든 층을 알아도 된다.

1-1. 맵은 프론트가 그린다 — 백엔드에 미치는 영향

v0.4에서 평면도를 프론트가 직접 만들기로 하면서 백엔드에서 사라진 것들이다.

사라진 것이유
GET /stores/{key}/map 엔드포인트폐기 확정
Store.map_width / map_image / entrance_*좌표를 서버가 갖지 않음
Scene.shape / points / radius동일
ETag / Cache-Control: public 처리전용 GET 엔드포인트가 없어짐
도면 이미지 S3 업로드프론트 정적 자산으로 이동

서버는 "어느 전시존에 어떤 상품이 속하는지"라는 논리 구성만 갖는다. 그게 화면 어디에 그려지는지는 프론트의 몫이다.

Scene에는 좌표 대신 no(번호) 가 들어간다. 프론트가 하드코딩한 도형과 scene.no를 매칭하고, 챗봇도 "1번 진열대"로 부를 수 있다.

이 방식의 대가는 매장이 늘어날 때 프론트 배포가 필요하다는 점이다. 지금은 매장 1개 고정이라 비용이 발생하지 않는다.

4. 인증 클래스

python

# api/authentication.py
from rest_framework.authentication import BaseAuthentication
from apps.visits import services as visits

class VisitTokenAuthentication(BaseAuthentication):
    """X-Visit-Token → Visit. DRF의 request.auth 에 Visit 객체를 넣는다."""

    def authenticate(self, request):
        token = request.headers.get("X-Visit-Token")
        if not token:
            raise exceptions.NotAuthenticated()
        try:
            visit = visits.authenticate(token)
        except visits.InvalidVisitToken:
            raise exceptions.AuthenticationFailed("INVALID_VISIT_TOKEN")
        return (AnonymousUser(), visit)      # request.auth == visit

뷰에서는 이렇게 쓴다.

python

# api/v1/events/views.py
class EventView(APIView):
    authentication_classes = [VisitTokenAuthentication]

    def post(self, request):
        visit = request.auth                 # 이미 확정된 Visit
        result = events.append_batch(visit, request.data["events"])
        return Response({"accepted": result.accepted,
                         "duplicated": result.duplicated}, status=202)

request.auth에 Visit을 담는 게 핵심이다. 모든 뷰가 visits.authenticate()를 직접 부르지 않아도 되고, 인증을 빠뜨린 뷰는 request.auth가 None이라 즉시 터진다.

5. 에러 포맷 통일

명세서 규약: { "error": { "code", "message", "detail" } }

python

# api/exceptions.py
def custom_exception_handler(exc, context):
    response = drf_exception_handler(exc, context)
    if response is None:
        return None

    code = getattr(exc, "error_code", DEFAULT_CODES.get(response.status_code))
    response.data = {
        "error": {
            "code": code,
            "message": str(exc.detail) if hasattr(exc, "detail") else str(exc),
            "detail": getattr(exc, "detail_obj", None),
        }
    }
    return response


DEFAULT_CODES = {
    400: "VALIDATION_ERROR",
    401: "UNAUTHORIZED",
    403: "FORBIDDEN",
    404: "NOT_FOUND",
    409: "CONFLICT",
    429: "RATE_LIMITED",
    500: "INTERNAL_ERROR",
}

8. Django 특유의 함정 5개

① VisitScopedManager가 Django 내부를 깨뜨린다

get_queryset()에서 예외를 던지면 역참조(visit.event_set), dumpdata, 마이그레이션이 전부 터진다. Django 내부가 기본 매니저를 쓰기 때문이다.

해결: 매니저 정의 순서와 base_manager_name

python

class Event(models.Model):
    all_objects = models.Manager()          # ① 먼저 정의 → _default_manager
    objects = VisitScopedManager()          # ② 개발자가 실수로 쓰는 이름

    class Meta:
        base_manager_name = "all_objects"   # 역참조·내부용

첫 번째로 정의된 매니저가 _default_manager가 되므로 Django 내부는 all_objects를 쓰고, 개발자가 무심코 Event.objects.all()을 쓰면 예외가 난다. 이 설정은 반드시 테스트로 확인해야 한다 — Django 버전에 따라 동작이 미묘하게 다르다.

② admin이라는 이름을 쓰지 않는다

apps.admin을 만들면 django.contrib.admin과 import 경로가 헷갈리고, INSTALLED_APPS에서 label 충돌이 난다. apps.dashboard로 둔다.

우리 서비스에는 Django admin 화면이 필요 없으므로 django.contrib.admin 자체를 INSTALLED_APPS에서 빼는 것도 방법이다. 브랜드 대시보드는 우리가 만든 API를 쓰고, 데이터 수정 경로는 없는 게 맞다.

③ FK는 문자열로 참조한다

python

visitor = models.ForeignKey("identity.Visitor", ...)   # ✓

클래스를 직접 import하면 app 간 순환 import가 생긴다. 우리 의존 규칙("같은 층끼리 import 금지")을 지키려면 문자열 참조가 필수다.

④ SSE는 WSGI에서 안 된다

/chat 스트리밍 때문에 ASGI로 띄워야 한다.

bash

uvicorn config.asgi:application

WSGI(gunicorn 기본)에서는 StreamingHttpResponse가 버퍼링되어 청크가 한 번에 나간다. 개발 서버에서는 되는데 배포하면 안 되는 대표적인 경우다.

⑤ React에서 EventSource로는 /chat을 못 부른다

브라우저 EventSource API는 커스텀 헤더를 실을 수 없다. X-Visit-Token을 보낼 방법이 없다.

javascript

// ✗ 헤더를 넣을 수 없다
new EventSource("/api/v1/chat");

// ✗ 토큰이 URL·서버 로그·리퍼러에 남는다
new EventSource(`/api/v1/chat?token=${token}`);

fetch + ReadableStream으로 직접 읽어야 한다.

javascript

const res = await fetch("/api/v1/chat", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-Visit-Token": token,          // ← 헤더로 안전하게
  },
  body: JSON.stringify({ visit_id, message }),
});

const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += value;

  for (const line of buffer.split("\n\n")) {
    if (!line.startsWith("data: ")) continue;
    const payload = JSON.parse(line.slice(6));
    if (payload.delta) appendToUI(payload.delta);
    if (payload.error) showError(payload.error);
    if (payload.done)  finish(payload.message_id);
  }
  buffer = buffer.slice(buffer.lastIndexOf("\n\n") + 2);
}

서버 구현에는 영향이 없다. SSE 포맷(data: {...}\n\n)을 그대로 내보내면 되고, 클라이언트가 EventSource 대신 수동 파싱을 할 뿐이다.

/chat이 POST인 것도 이 결정과 맞물린다. EventSource는 GET만 지원하므로 애초에 쓸 수 없는 설계다.
