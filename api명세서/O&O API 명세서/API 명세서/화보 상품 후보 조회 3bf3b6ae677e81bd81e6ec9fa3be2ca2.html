이 API는 DB만 읽는다. 워커도 스토리지도 이미지 생성 API도 안 써서 가장 먼저 만들 수 있다.

설명

관람 중 쌓인 행동 기록과 챗봇 대화에서 화보에 담을 만한 상품 6개를 뽑아 준다. Figma P01이 6칸 그리드라 개수를 6으로 고정한다.

사용자는 그중 1개를 고른다. 선택은 서버로 보내지 않고 클라이언트가 들고 있다가 생성 요청에 실어 보낸다.

Response 200

{
  "max_select": 1,
  "min_select": 1,
  "preselected": ["p_101"],
  "items": [
    {
      "product_id": "p_101",
      "name": "Heritage 미니백",
      "category": "미니백",
      "thumbnail": "https://cdn.../p_101_t.jpg",
      "cutout_url": "https://cdn.../p_101_c.png",

      "reason": "오늘 가장 오래 보신 상품"
    }

}

items는 정확히 6개. 후보가 부족하면 인기순으로 채운다.

max_select를 서버가 내려주는 이유 — 지금은 1개지만 Figma 원안은 최대 4개였다. 나중에 늘릴 때 API 계약도 프론트 코드도 안 바꾸고 숫자만 바꾸면 된다.

점수 산출

행동 데이터와 챗봇 데이터를 함께 쓴다.

소스신호가중
eventsproduct_dwell.dwell_ms (log 정규화)0.35
eventsproduct_view 반복 (최대 3회)0.15
chat_logs대화에 등장한 상품0.15
reports.payloadpreference_tags ↔ products.features0.25
reports.payloadavoid_tags ↔ features-0.20
productsnewness0.10

체류시간이 가장 강한 신호다. 그냥 본 것보다 오래 머문 상품에 큰 점수를 준다는 기존 원칙 그대로다.

순위도 근거도 LLM에 맡기지 않는다. AI가 만든 건 preference_tags / avoid_tags뿐이고, 그걸 재료로 쓰는 계산은 전부 결정론적이다. AI 구조도의 스코어링과 같은 방식이다.
대화가 없는 방문은 chat·prefer·avoid 항목이 0이 되고 행동 신호만으로 순위가 나온다. 후보 6개는 항상 채워진다.

reason_code

가중치 x 점수가 가장 큰 항목에서 기계적으로 정한다.

code문구
most_dwelled오늘 가장 오래 보신 상품
revisited여러 번 돌아와 보신 상품
chat_mentioned챗봇에서 물어보신 상품
taste_match선호하신 소재·색과 맞아요
new_arrival이번 시즌 신상품

카드에 뱃지로 노출한다. "내가 오래 본 거네"라는 인지가 있어야 선택률이 올라간다. Figma P01 카피가 이미 그 방향이다.

프론트는 lookbook_product_select 이벤트에 reason_code를 함께 담는다. 어떤 추천 근거가 실제 선택을 유도했는지 알 수 있고, 가중치 조정의 근거가 된다.

cutout_url

배경이 제거된 상품 PNG. 화보 합성에 쓴다.

상품 CSV 준비 단계에서 미리 만들어 두세요. 생성 시점에 배경 제거를 돌리면 대기시간이 몇 배가 되고, 상품 이미지에 배경이 남아 있으면 합성 결과가 확 나빠진다. 데모 품질을 가장 크게 좌우하는 준비 작업이다.
