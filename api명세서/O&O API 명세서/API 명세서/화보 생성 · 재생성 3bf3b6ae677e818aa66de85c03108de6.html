큐에 넣고 즉시 202를 반환한다. /finish와 같은 패턴이다.

Request

{
  "product_ids": ["p_101"],
  "photo_key": "photos/2026/08/17/9c1f4a2b.jpg",
  "mask_key": "photos/2026/08/17/9c1f4a2b_mask.png",
  "consent": true,
  "photo_meta": {
    "face_count": 1,
    "face_ratio": 0.18,
    "face_center": [0.5, 0.35]
  }
}

mask_key와 photo_meta는 선택이다. 없으면 각각 일반 생성 / 전체 구도 후보로 떨어진다. 검출이 실패해도 서비스는 정상 동작한다.

Response 202

{
  "job_id": "job_7f3a2c",
  "share_slug": "look-x9y8z7",
  "attempt": 1,
  "remaining_regenerations": 2,
  "poll_after_ms": 3000
}
share_slug를 여기서 미리 준다. 프론트가 history.replaceState('/l/look-x9y8z7')로 URL을 바꿔두면 로딩 중 앱을 닫았다 켜도 복구된다. 리포트 slug와 같은 원리다.

서버 처리 순서

① 토큰 ↔ slug 방문 일치            불일치 → 403
② report.status == ready          아니면 → 409 report_pending
③ len(product_ids) <= max_select   초과 → 400 too_many_products
④ 상품이 해당 매장 것인가          아니면 → 400 unknown_product
⑤ consent == true                  아니면 → 400 consent_required
⑥ S3 HEAD — 실제로 올라왔나        없으면 → 400 upload_not_found
⑦ 매직바이트 12B — 진짜 이미지인가  아니면 → 400 not_an_image
⑧ attempt = max(attempt) + 1 <= 3  초과 → 429 regeneration_limit
⑨ 구도 후보 필터 + seed 선택
⑩ Lookbook insert + Redis 초기화 + image 큐 적재 → 202
⑥⑦이 필요한 이유 — presign의 content_type은 클라이언트가 선언한 값이라 실제 내용과 무관하다. image/jpeg라고 해놓고 아무거나 올릴 수 있다.
⚠️ ⑧을 select_for_update로 감쌀 것. [다시 돌리기] 연타 시 같은 attempt가 두 번 계산되면 이미지 생성 비용이 두 배로 나간다. UniqueConstraint(report, attempt)가 최악은 막아주지만 그때 500이 뜨니 409로 변환도 필요하다. 프론트도 버튼을 즉시 disabled로.

체형 보존 — 인페인팅

프롬프트로 "체형을 유지하라"고 쓰는 것만으로는 부족하다. 이미지 생성 모델은 텍스트보다 입력 이미지에 강하게 반응하고, 대부분 자동으로 얼굴을 갸름하게·몸을 날씬하게 만든다. 이게 결과가 나로 안 보이는 주된 원인이다.

인물 영역을 생성 대상에서 빼는 것이 구조적 해법이다.

재생성

같은 엔드포인트를 product_ids·photo_key 그대로 재호출한다. 재촬영도 재선택도 불필요하다.

attempt1 → 2 → 3
share_slug매번 새로 발급
이전 화보삭제하지 않음
4회차429 regeneration_limit
새 share_slug를 주는 이유 — 이미 공유한 링크의 이미지가 바뀌면 남이 열었을 때 다른 화보가 보인다. 박제 위반이다. 새 slug를 주면 공유된 링크는 그대로 살아 있다.
횟수 제한이 필요한 이유 — 이미지 생성은 호출당 비용이 붙는다. 무제한이면 방문자 재량으로 비용이 늘어난다. 3회면 "마음에 안 들면 두 번 더"라 UX상 충분하다.

워커

image 큐로 보낸다. 뷰에서 직접 생성하지 않는다 — 15~40초짜리 호출이 uvicorn 프로세스를 물면 동시 2명에 서비스가 멈춘다.

① Redis에 진행률 기록
② R2에서 사진·마스크 다운로드
③ 이미지 생성 API 호출        ← 여기가 15~40초
④ 결과를 R2에 저장           ★ 먼저
⑤ DB에 image_url + ready      ★ 나중
⚠️ ④⑤ 순서를 뒤집으면 안 된다. DB에 ready인데 이미지가 아직 없으면 사용자가 404를 본다. 반대 순서는 몇 밀리초 더 기다릴 뿐이라 안전하다. 완료 표시는 항상 맨 마지막에.
