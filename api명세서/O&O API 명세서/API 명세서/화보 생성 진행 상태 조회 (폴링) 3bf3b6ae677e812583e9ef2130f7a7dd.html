왜 Redis만 읽나

화보 하나당 폴링이 8~9번이다. 동시 100명이면 3초마다 100번, 초당 33회 DB 조회가 발생하고 그게 전부 똑같은 답을 가져온다.

Redis 조회는 0.1ms라 초당 3,300번도 문제가 없다. 그리고 진행률 40%였다는 기록은 나중에 아무도 안 찾으니, 휘발성 데이터는 휘발성 저장소에 두는 게 맞다.

화보 하나당 DB 조회가 10회에서 2회로 줄어든다.

상태 머신

              └─▶ failed
status프론트
queued / processing로딩 화면 유지 (색상 카드 회전)
ready완성본 조회로 이동 → P03
failed • retryable: true[다시 시도] — 횟수 차감 없음
failed • retryable: false에러 안내

단계

progressstagestep
0.10compose화보를 준비하는 중
0.35render패디가 셔터를 누르는 중
0.90finalize화보를 마무리하는 중
프론트는 step 문자열이 아니라 stage 코드로 분기한다. 카피 한 글자만 바꿔도 애니메이션이 깨지면 곲4란하다.
Figma의 COLOR / ITEM / MOOD 색상 카드 연출은 프론트 연출이다. 카드에 쓸 색은 GET /reports/{slug}의 mood.palette를 그대로 쓴다 — 이미 받아둔 값이라 추가 호출이 없다.

진행률 시간 보간

워커는 AI 응답을 기다리는 25초 동안 멈춰 있어 Redis를 갱신할 수 없다. 그대로 두면 40%에서 25초간 멈춰 있게 된다.

그래서 워커는 시작 시각만 남기고, Django가 폴링에 답할 때 경과 시간으로 그 사이를 채운다.

progress = 0.35 + 0.55 x min(경과 / LOOKBOOK_EXPECTED_SEC, 1.0)
90%를 넘기지 말 것. 예상보다 늦어졌는데 99%에서 멈춰 있으면 오히려 더 답답하다. 90%에서 대기하다 진짜 끝나면 100%로 점프시킨다.
LOOKBOOK_EXPECTED_SEC은 벤더 실측 p50을 써야 한다. 25초로 가정했는데 실제가 40초면 90%에서 오래 멈춰 있게 된다.

poll_after_ms

서버가 매번 내려주고 클라이언트는 따르기만 한다.

경과간격
15초 미만3000ms — 어찌피 안 끝난다
15초 이후1200ms — 완료 임박

부하 조절 손잡이를 서버가 쥐고 있는 구조라, 데모 당일 사람이 몰려도 배포 없이 대응할 수 있다.

값retryable사용자 안내

Redis 미스 폴백

TTL 300초가 지났거나 Redis가 죽었으면 DB에서 읽어 답한다. 서비스는 계속 돌고 조금 느려질 뿐이다.

폴링이 SSE보다 나은 이유

SSE는 연결이 유지되는 25초 내내 uvicorn 워커 하나를 붙잡고 있다. 화보 생성을 워커로 미룬 이유가 "25초짜리가 웹 프로세스를 물면 안 된다"였는데, SSE를 잘못 붙이면 같은 문제를 다시 만든다.

폴링은 요청이 0.01초에 끝나서 워커를 금방 놓아준다. 사용자가 화면을 보고 있는 25초짜리 작업에는 폴링이 가장 단순하고 안 깨진다.
