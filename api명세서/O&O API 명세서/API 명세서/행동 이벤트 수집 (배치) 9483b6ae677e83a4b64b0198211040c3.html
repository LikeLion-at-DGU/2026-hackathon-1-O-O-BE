설명

프론트가 모아둔 행동 기록을 한번에 묶어서 보낸다. 매 클릭마다 서버를 치지 않고, 주기적으로 또는 페이지를 떠날 때 보내서 브라우저가 닫혀도 직전 기록이 날아가지 않게 한다.

저장은 append-only — 쌓기만 하고 고치지 않는다. 같은 이벤트를 두 번 보내도 event_id로 걸러 한 번만 저장하므로(멱등), 실패하면 그냥 재전송하면 된다.

이벤트 타입별 역할

매장 / 방문

event_type언제어떤 역할인지
store_enter입장 버튼을 눌러 들어왔을 때관람의 시작점. 퍼널 계산의 분모가 된다
visit_start방문이 시작될 때체류시간 측정의 기준 시각
visit_end관람이 끝났을 때총 체류시간 확정. 리포트 분석의 신호

전시존 (매대)

event_type언제어떤 역할인지
scene_view전시존 화면에 들어갔을 때어떤 존이 사람을 끌어당기는지 (유입)
scene_dwell그 존에 머문 시간어떤 구역에 관심이 쏠리는지. 진열 구성 개선 근거
hotspot_click존 안의 상품 핫스팟을 눌렀을 때존에서 상품으로 넘어간 전환. 진열이 잘 먹혔는지

상품 (취향 분석의 핵심 재료)

event_type언제어떤 역할인지
product_view상품 상세를 열었을 때기본 관심 신호. 가장 약한 가중치
product_dwell그 상품에 머문 시간가장 중요한 신호. 오래 볼수록 관심이 크다고 본다
같은 상품을 다시 본 횟수(재조회)도 product_view가 여러 번 쌓이는 걸로 계산한다. 한 번 오래 본 것과 여러 번 돌아온 것 모두 관심으로 친다.

챗봇

event_type언제어떤 역할인지
chatbot_open챗봇을 열었을 때정보를 더 원한다는 신호
question_submit질문을 보냈을 때무엇을 궁금해하는지. 행동으로 안 드러나는 취향·망설임을 잡는 통로
recommendation_impression챗봇이 추천을 띄웠을 때추천이 실제로 노출됐는지 (클릭률의 분모)
recommendation_click그 추천을 눌렀을 때추천이 먹혔는지. 추천 로직 성능 측정

⚠️ 관람 끝 버튼을 누를 때 — 마지막 구간 유실 방지

배치 전송이라 항상 "아직 안 보낸 버퍼"가 있다. 그런데 /finish가 방문을 종료시키면 토큰이 즉시 무효가 되어, 그 뒤에 도착한 /events는 401을 맞는다.

T+0.0  마지막 상품을 30초간 봄  → 버퍼에 쌓임 (전송 전)
T+3.0  "관람 끝" 클릭     → /finish → 종료
T+3.2  버퍼 전송           → 401  ✗ 유실

하필 종료 직전 구간이라 관심도가 가장 높은 데이터다.

해결 — /finish가 마지막 요청이 되게 한다

프론트가 순서를 지킨다.

disableButton();
setLoading("관람 기록을 정리하고 있어요");

await Promise.race([flushPending(), sleep(3000)]);   // ① 진행 중인 요청 대기 (상한 3초)
const { slug } = await post("/visits/{visit_id}/finish", {
  events: buffer.drain(),                            // ② 남은 버퍼 동봉
});
pollReport(slug);                                    // ③

3초를 넘겨 중복 전송이 되어도 안전하다. event_id 멱등이라 서버가 duplicated로 세고 버린다.

로딩 대기는 어찌피 필요하다(워커 3~4초). 이벤트 flush(수백 ms)는 그 안에 흡수되어 사용자가 추가로 기다리는 시간은 사실상 없다.

버튼을 안 누르고 창을 닫는 경우엔 마지막 배치 주기만큼(10~15초) 잃는다. 그 앞 데이터는 전부 남는다.

배치 제약

항목값
한 요청 최대 이벤트 수100개 (초과분은 버림)
전송 주기 권장10~15초
순서 보장없음 — client_timestamp로 정렬하므로 무관
부분 성공허용 — 잘못된 건만 버리고 나머지는 저장

배치 10건 중 1건이 스키마 위반일 때 전부 거부하면 9건까지 잃는다. 행동 로그는 정합성보다 수집률이 중요하다.
