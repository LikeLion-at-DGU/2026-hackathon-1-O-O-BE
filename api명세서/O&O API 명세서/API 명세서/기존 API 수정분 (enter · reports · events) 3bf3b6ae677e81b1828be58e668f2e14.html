① 토큰 만료 조건 변경 (공통 규약)

기존
 ① /finish 호출 즉시 만료
 ② 진입 후 3시간

변경
 ① 진입 후 3시간 — 이것 하나만

화보와 재생성이 /finish 이후에 일어나기 때문이다. 기존 규약대로면 [다시 돌리기]를 누를 수가 없다 — 화보가 완성된 그 화면에서 누르는 버튼인데 토큰이 이미 죽어 있다.

①이 있던 이유(리포트 박제 보호)는 /events 타입 화이트리스트가 전담한다. 같은 일을 두 군데서 막고 있었고, 그중 토큰 쪽이 화보를 방해했다.

3시간이면 관람(20분~1시간) + 화보 + 재생성 3회가 충분히 들어간다.

⚠️ settings.VISIT_STALE_AFTER가 현재 24시간으로 박혀 있다. 공통 규약은 3시간이고 근거까지 적혀 있는데 코드만 안 고쳐졌다. 문서 충돌이 아니라 이미 코드로 내려온 건이라 더 급하다.

② POST /enter — 필드 추가

{
  "muse_no": 14,
  "muse_label": "N.014",
  "is_resumed": false,
  "is_new": true
}

muse_no — Figma 랜딩 L04 "당신의 번호를 등록할게요" → N.014. 매장 카운터를 select_for_update로 증가시켜 발급한다. 둘이 동시에 입장하면 둘 다 N.014가 될 수 있다.

재진입(is_resumed=true) 시에는 새로 발급하지 않는다. 뒤로가기 한 번에 번호가 올라가면 안 된다.

is_resumed / is_new — 본문 여러 곳에서 언급되지만 응답 정의에는 빠져 있던 항목이다. 프론트가 응답 스펙만 보고 구현하면 재진입 분기를 못 만든다. 이 참에 같이 넣는다.

③ GET /reports/{slug} — 필드 추가

{
  "mood": { "code": "cognac_noir", "name": "COGNAC NOIR",
             "reason": "...", "palette": ["#6B3F26", "#1C1614", "#C9A227"] },
  "stats": [ { "key": "cuts", "label": "컷수", "value": 32 } ],
  "recommendations": [ { "cutout_url": "https://cdn.../p_101_c.png" } ],
  "lookbook": {
    "status": "none",
    "share_slug": null,
    "job_id": null,
    "attempts_used": 0
  }
}

mood가 여기 실리므로 별도 무드 API가 필요 없다. P02는 이미 받아둔 값을 보여주기만 한다. 로딩 화면의 색상 카드도 mood.palette를 그대로 쓴다.

lookbook은 새로고침·재진입 시 어느 화면으로 갈지 판단하는 근거다.

워커 파이프라인 변경

① 이벤트 집계        계산
② 관심도             계산
③ confidence         계산
④ AI② 태그 추출       LLM 1회
⑤ 취향 벡터           계산
⑥ 스코어링            계산
⑦ 무드 판정           계산   ← 신규 (기존 16유형 매핑 자리)
   → reports.payload.mood 저장 → status: ready

⑤의 취향 벡터와 ④의 태그를 재료로 무드를 판정한다. LLM 호출이 추가되지 않는다.

기존 ⑦의 characters 이미지 조회는 삭제한다 (사전 제작 16장 폐기).

무드에는 랜덤을 넣지 않는다. 리포트는 한 번만 만들어지고 박제된다. 랜덤은 화보 생성 시점의 구도 선택에만 들어간다.

종료 후 화이트리스트

visits.ended_at 이 채워진 뒤:
  lookbook_* , photo_*          → 정상 수집
  product_* , scene_* , chat_*  → 409 CONFLICT (무시, 로그만)

리포트는 /finish 시점에 박제되므로 관람 이벤트가 뒤늦게 들어와도 반영될 수 없다. 원본과 리포트가 어긋나는 걸 여기서 막는다.

lookbook_product_select에 reason_code를 함께 담을 것. 어떤 추천 근거가 실제 선택을 유도했는지 알 수 있고, 다음에 가중치를 조정할 근거가 된다.
lookbook_regenerate 비율이 높으면 화보 품질이나 프롬프트에 문제가 있다는 신호다.

이벤트 100개 상한

현재 명세는 "한 요청 최대 100개, 초과분은 버림"이다. 버리지 말고 다음 배치로 넘기는 것을 권한다.

네트워크가 끊겼다 복구되면 밀린 버퍼가 한 번에 몰리는데, 매장 와이파이에서 충분히 일어난다. 그때 버려지는 건 클라이언트에도 서버에도 기록이 안 남는다.

{ "accepted": 98, "duplicated": 1, "rejected": 3 }

rejected 수를 응답에 실어 프론트가 알 수 있게 하면 된다.
