설명

관람을 마치면 호출한다. 서버는 분석 작업을 백그라운드로 넘기고 리포트 주소(slug)를 발급해 바로 응답한다. 같은 visit_id로 다시 호출해도 같은 slug가 나온다(멱등).

퇴장 설문은 받지 않는다. 연령대·성별도 입장할 때 이미 받았으므로 여기서는 아무것도 입력받지 않는다.

Request

바디는 비워도 된다({}). events는 프론트에 남은 이벤트 버퍼를 동봉하는 용도다.

{
  "events": [
    { "event_id": "e_88", "event_type": "product_dwell", "product_id": "p_101",
      "client_timestamp": "2026-08-18T06:20:00Z", "metadata": { "dwell_ms": 30000 } }
  ]
}

왜 여기서 이벤트를 받나

종료되면 그 방문은 쓰기가 막힌다. 남은 버퍼를 /events로 따로 보내면 거부당해 관람 직전 구간이 통째로 사라진다. 관심도가 가장 높은 구간이라 손실이 크다.

동봉하면 요청이 하나라 레이스도 유예 시간도 필요 없다.

Response 202

{
  "slug": "r_7Ka9xQ",
  "status": "pending",
  "events": { "accepted": 3, "duplicated": 1, "ignored": 0, "rejected": 0 }
}

재전송해도 안전하다 — event_id(이벤트)와 visit_id(slug) 양쪽에 멱등이 걸려 있다.

서버 처리 순서 (한 트랜잭션)

① 남은 이벤트 저장 → ② 방문 종료(visit_end 기록) → ③ 분석 큐 적재 → slug 반환

중간 상태("이벤트는 저장됐는데 종료가 안 된")가 존재하지 않는다. 이 순서 덕분에 워커가 완전한 데이터로 분석한다.

분석 워커

단계하는 일
① 이벤트 집계상품별 조회·재조회·체류·챗봇 언급으로 압축
② 관심도log 가중합. 한 상품만 30번 본 사람이 프로필을 지배하지 않게
③ confidence조회 40% / 체류 30% / 질문 20% / 찜 10%
④ 취향 추출 (LLM)대화에서 선호·비선호 태그. 대화가 없으면 호출을 건너뛴다
⑤ 취향 벡터개별 상품 선호 → 8개 축 선호로 변환
⑥ 스코어링개인 취향 75% + 인기 15% + 신상품 10% + 미조회 발견 가산
⑦ 16유형 매핑4축 부호로 결정론적 매핑
⑧ 리포트 조립상품 스냅샷 박제 → status: ready

LLM이 붙는 ④만 수 초가 걸리고 나머지는 순수 연산이다. 그래서 /finish는 slug만 즉시 반환한다.

알아둘 것

워커가 백그라운드 스레드로 돈다. 배포 중 systemctl restart를 하면 진행 중인 분석이 사라진다. 데모 중에는 생성 작업이 없는 순간에 재배포한다.

  • 이벤트가 0건인 방문에서도 죽지 않는다. confidence: 0.0 · is_exploring: true로 나가고 추천은 인기순으로 채워진다
  • 무드 판정은 아직 미구현이다. 리포트 payload에 mood가 실리지 않아 화보 로딩 화면의 색상 카드를 아직 쓸 수 없다
