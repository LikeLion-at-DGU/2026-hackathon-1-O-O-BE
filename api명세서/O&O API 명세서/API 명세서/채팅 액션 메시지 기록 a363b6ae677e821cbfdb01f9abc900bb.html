설명

O&O의 챗봇은 처음부터 대화창이 아니라 사용자의 클릭이 그대로 메시지로 쌓이는 타임라인이다. 진열대를 누르면 "1번 진열대 클릭", 상품을 누르면 "OO 상품 클릭"이 말풍선으로 남는다.

이 API는 그 액션 메시지를 chat_logs에 기록한다. 나중에 사용자가 "채팅으로 대화하기"로 넘어갔을 때, 서버가 이 기록을 그대로 읽어 AI가 "지금 어떤 상품 얘기를 하는 중인지"를 알게 하는 게 목적이다.

회화 내역은 화면을 이동해도 지워지지 않는다. 같은 visit_id로 계속 쌓인다.

그리고 이 기록은 리포트 분석(AI ②) ③′단계의 입력이다. 행동만으로는 안 드러나는 망설임이 여기서 나온다.

행동 기록(/events)과의 차이

역할
POST /events분석용 원본 행동 로그. 체류시간·횟수 같은 수치를 쌓는다
POST /chat/messages화면에 보이는 대화 타임라인 + AI 문맥. 사람이 읽는 메시지

진열대를 한 번 누르면 보통 둘 다 호출한다(분석용 이벤트 + 화면용 메시지).

클라이언트가 보낸 문장이 그대로 AI 프롬프트에 들어가면 안 되기 때문이다.

{ "visit_id": "v_9f8e...", "type": "product_click", "product_id": "p_101" }

필드설명
messages이번 호출로 새로 쌓인 말풍선 전부. 프리셋·트리거 응답은 2개 이상이 될 수 있다
recommendationshypothesis_yes 직후 등 서버가 추천을 낸 경우에만 채워진다
profile_completion뮤즈 프로필 완성도 (0~1). 리포트의 confidence와 같은 값이다 — 계산은 한 곳뿐이고 필드명만 다르다
  • 201 = 말풍선을 새로 쌓았다
  • 200 = 직전과 같은 클릭이라 쌓지 않고 기존 메시지를 돌려줬다 (아래 참고)

직전과 같은 클릭은 쌓지 않는다

같은 진열대·상품을 연속으로 누르면 화면이 같은 말풍선으로 도배된다. 그래서 직전 액션과 문구가 같으면 새로 쌓지 않고 200 을 준다.

수치는 잃지 않는다 — 조회 횟수는 POST /events가 따로 남기므로, 말풍선이 1개여도 이벤트는 5건 그대로 쌓인다.

판정은 연속일 때만이다.

상황동작
A → A → A첫 번째만 쌓고 나머지 건너뜀
A → B → A (돌아옴)다 쌓임
상품A → 상품B → 상품A (왕복)다 쌓임 — 비교 신호라 접으면 안 된다
상품A → 프리셋 → 상품A다 쌓임

프리셋은 중복 제거 대상이 아니다. 같은 걸 다시 물어보는 것 자체가 의미 있는 행동이다.

프리셋을 누르면 말풍선이 2개 생긴다

                            가격        ← user_action (누른 버튼)
🐻 890,000원입니다. 엔트리 가격대예요.    ← preset (미리 작성된 답변)

프리셋 버튼 3개는 상품 문맥이 유지되는 동안 계속 노출한다. 다시 물어볼 수 있어야 한다.
products.preset_answers에 문구가 비어 있으면 폴백 문장이 나가고 서버 로그에 경고가 남는다.

대화 내역 불러오기 — GET /chat/messages

"채팅으로 대화하기"로 넘어갔을 때, 화면을 이동했을 때, 이어하기로 돌아왔을 때 이전 메시지를 그대로 보여주기 위해 사용한다.

  • 페이지네이션 없음. 전량 반환한다(최근 200개 상한). 화면과 AI 문맥이 모두 전체를 본다
  • 첫 인사는 서버가 입장 시 적립한다. 프론트가 하드코딩하지 않는다 — 이 호출 하나로 화면이 완전히 복원돼야 하고, 이어하기로 돌아왔을 때도 인사가 제자리에 있어야 한다
  • current_context 는 가장 최근에 클릭한 진열대·상품이다. POST /chat이 이걸 기본 문맥으로 쓴다. 상품만 클릭했어도 scene_id가 채워진다(그 상품이 속한 존) — 챗봇이 "3번 진열대 2번 상품"으로 안내해야 하므로 존 정보가 비면 안 된다
  • pending_action 은 지금 답해야 할 버튼이다. 없으면 null. 저장하지 않고 파생 계산한다 — 마지막 assistant 메시지가 가설이고 아직 응답이 없으면 생성된다
  • 종료된 관람도 읽을 수 있다. 퇴장 후 리포트를 기다리는 동안에도 대화를 봐야 한다

role 값

role의미
assistant챗봇(곰) 메시지 — 인사, 트리거 가설, 추천 안내, POST /chat 답변

트리거 가설은 assistant, 맞아요/아니에요는 user_action이다. 역할 값은 4종에서 늘지 않는다.

트리거 가설은 서버가 만든다

클라이언트가 요청하지 않는다. 서버가 POST /events 배치를 받은 직후 조건을 평가해 assistant 말풍선을 타임라인에 넣는다. 프론트는 GET /chat/messages나 POST /events 이후 갱신에서 발견한다.

트리거예시 문장
같은 상품 재조회 2회+"이 백팩에 다시 돌아오셨네요. 마음에 남으셨어요?"
한 상품 체류 30초+"오래 보고 계세요. 이런 쪽이 끌리시나요?"
왕복 조회 (A→B→A)"두 개를 견주고 계시네요. 어느 쪽이 더 끌리세요?" (2택)
축 확인 (7조건 충족)"진열대를 옮겨가면서도 블랙 위주로 보셨네요. 색은 이쪽이 편하세요?"
회피 (존 내 미조회)"화려한 색은 눈에 안 들어오시는 것 같아요. 차분한 쪽이 편하세요?"
빠른 훑기"찾으시는 게 있으세요?" (매일 쓸 것 / 특별한 날 / 그냥 둘러봐요)

문구는 손님용 표현을 쓴다. y2k_street → "스트리트한 느낌", coated_canvas → "생활 방수 되는 소재". 내부 축 값을 그대로 말하지 않는다. 전체 대응표는 docs/챗봇_로직.md의 「손님용 어휘」에 있다(단일 출처).

빈도 제한: 확인형 총 방문당 3회(축 확인 1회 예약) · 같은 축 1회 · 워밍업(상품 3개 조회 + 입장 60초 후) · 확인 사이 상품 2개 조회 간격.
그냥 둘러봐요를 선택하면 그 방문에는 더 묻지 않는다.

hypothesis_yes 응답 시 서버는 즉시 추천 3개를 함께 돌려준다. 확인의 대가로 새 물건을 받아야 사용자가 왜 답했는지 안다.

hypothesis_no는 트리거 종류에 따라 처리가 다르다.

트리거아니에요 처리
상품 확인그 상품을 관심 상품 집합에서 제외 + "무엇이 걸리세요?" 채팅 유도
축 확인 · 회피형가설 축 감점 + 그 축은 이번 방문에 다시 묻지 않음 + 채팅 유도

프론트가 지켜야 할 것

  • 멱등 키가 없다. 실패 시 재전송하면 말풍선이 중복된다. 재시도하지 말 것 — 수치는 /events가 담당하므로 말풍선 하나가 빠져도 분석에 영향이 없다
  • visit_id는 토큰이 가리키는 방문과 같아야 한다
  • 트리거 버튼을 누를 때 reply_to를 반드시 함께 보낸다 (중복 클릭·시차 방어)
