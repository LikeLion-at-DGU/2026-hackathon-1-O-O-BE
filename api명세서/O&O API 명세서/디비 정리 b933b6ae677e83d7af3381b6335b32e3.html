디비 정리

DB 설계

모듈 문서에 흩어진 모델을 한 곳에 모은 것.
핵심 질문 하나를 먼저 정리한다 — 채팅 기록을 사용자에 매달까, 방문에 매달까.

1. 채팅 기록은 visit에 매단다

결론부터: ChatLog.visit FK 하나면 사용자별 조회도 된다. visitor를 중복 저장하지 않는다.

python

class ChatLog(models.Model):
    visit = models.ForeignKey("visits.Visit", on_delete=models.CASCADE)
    # visitor FK 없음

왜 visit인가

대화의 맥락 단위가 방문이다. 오늘 "이 백팩 소재 뭐야?"라고 물은 것과 3개월 전 다른 매장에서 물은 것은 이어지는 대화가 아니다. 챗봇 히스토리를 visitor로 가져오면 몇 달 전 대화가 프롬프트에 섞인다.

그리고 visit이 이미 visitor를 가리키므로 사용자 단위 조회가 그대로 된다.

python

# 이번 방문의 대화 — 챗봇 프롬프트용
ChatLog.objects.for_visit(visit)

# 이 사용자의 전 대화 — 재방문자 분석용
ChatLog.all_objects.filter(visit__visitor=visitor)

# 이 사용자의 직전 방문 대화
ChatLog.all_objects.filter(
    visit=Visit.objects.filter(visitor=visitor).order_by("-entered_at")[1]
)

JOIN 한 번이 추가되지만 visits(visitor) 인덱스가 있어 비용이 없다시피 하다.

visitor FK를 중복으로 넣으면 안 되는 이유

python

# ✗ 이렇게 하지 않는다
class ChatLog(models.Model):
    visit = models.ForeignKey(Visit, ...)
    visitor = models.ForeignKey(Visitor, ...)     # 중복

두 값이 어긋날 수 있고(visit.visitor != chatlog.visitor), 무엇보다 보존기간 정책이 깨진다. privacy.purge_expired()가 오래된 이벤트를 visit=None으로 익명화할 때, visitor FK가 따로 남아 있으면 익명화가 무의미해진다.

다만 taste_profiles는 visitor에 매단다

취향은 방문 단위가 아니라 사람 단위로 누적되어야 한다. 리포트의 visit_summary.change_from_last("지난 방문보다 레더 관심이 늘었어요")가 이걸 필요로 한다.

ChatLog       → visit    (그때 그 대화)
Event         → visit    (그때 그 행동)
Report        → visit    (그때 그 결과, 박제)
TasteProfile  → visitor  (누적되는 취향)

2. DB는 PostgreSQL

PostgreSQLSQLite
JSONField 인덱스GIN 인덱스 지원없음
동시 쓰기행 단위 락DB 전체 락
bulk_create(ignore_conflicts)정상정상
집계 쿼리빠름느림

SQLite를 쓰면 안 되는 결정적 이유는 워커다. Celery 워커가 리포트를 쓰는 동안 웹 요청이 이벤트를 저장하려 하면 DB 전체가 잠긴다. 방문자 여러 명이 동시에 챗봇을 쓰는 순간 타임아웃이 난다.

로컬 개발도 Postgres로 통일하는 게 낫다. JSONField 동작이 달라서 로컬에서만 되는 코드가 나온다.

4. 테이블 정의

users — 익명 방문자

python

class Visitor(models.Model):
    id = models.CharField(max_length=32, primary_key=True,
                          default=lambda: gen_id("u"))     # u_a1b2c3
    anonymous_uuid = models.UUIDField(unique=True, db_index=True, default=uuid4)
    created_at = models.DateTimeField(auto_now_add=True)
    last_seen_at = models.DateTimeField(auto_now=True)

created_at이 신규/재방문 코호트의 기준이다.

visits — 방문 세션

python

class Visit(models.Model):
    id = models.CharField(max_length=32, primary_key=True,
                          default=lambda: gen_id("v"))     # v_9f8e...
    visitor = models.ForeignKey(Visitor, on_delete=models.CASCADE)
    store = models.ForeignKey("stores.Store", on_delete=models.PROTECT)
    token = models.CharField(max_length=43, unique=True, db_index=True,
                             default=lambda: secrets.token_urlsafe(32))
    entry_point = models.ForeignKey("stores.EntryPoint", null=True,
                                    on_delete=models.SET_NULL)
    entered_at = models.DateTimeField(auto_now_add=True)
    exited_at = models.DateTimeField(null=True)
    is_auto_closed = models.BooleanField(default=False)
    is_verified = models.BooleanField(default=False)

    class Meta:
        indexes = [
            models.Index(fields=["visitor", "store", "exited_at"]),   # start()
            models.Index(fields=["store", "entered_at"]),             # 대시보드
        ]

entry_point는 지금 항상 NULL이다. 채널 구분이 필요해질 때를 위한 자리만 열어둔다.

stores / scenes / products

python

class Brand(models.Model):
    name = models.CharField(max_length=100)


class Store(models.Model):
    id = models.CharField(max_length=32, primary_key=True,
                          default=lambda: gen_id("s"))
    brand = models.ForeignKey(Brand, on_delete=models.PROTECT)
    store_key = models.SlugField(unique=True)           # QR에 담기는 값
    name = models.CharField(max_length=100)
    is_active = models.BooleanField(default=True)
    map_width = models.IntegerField(default=720)
    map_height = models.IntegerField(default=600)
    map_image = models.URLField(null=True)
    entrance_x = models.IntegerField(default=0)
    entrance_y = models.IntegerField(default=0)
    allowed_ip_set = models.JSONField(default=list)     # 매장 내 판정용 (미사용)


class Scene(models.Model):
    id = models.CharField(max_length=32, primary_key=True,
                          default=lambda: gen_id("sc"))
    store = models.ForeignKey(Store, on_delete=models.CASCADE)
    code = models.SlugField()                  # scene_1, scene_2 ...
    label = models.CharField(max_length=8)     # 지도에 찍히는 "1"
    name = models.CharField(max_length=100)
    order = models.IntegerField()
    shape = models.CharField(max_length=10, default="rect")
    points = models.JSONField()                # [{"x":40,"y":40},{"x":110,"y":520}]
    radius = models.IntegerField(null=True)

    class Meta:
        unique_together = [("store", "code")]
        ordering = ["order"]


class Product(models.Model):
    id = models.CharField(max_length=32, primary_key=True,
                          default=lambda: gen_id("p"))
    scene = models.ForeignKey(Scene, on_delete=models.CASCADE)
    name = models.CharField(max_length=200)
    price = models.IntegerField()
    price_tier = models.CharField(max_length=16)
    content = models.TextField()
    image_set = models.JSONField(default=list)
    size_set = models.JSONField(default=list)
    features = models.JSONField(default=dict)     # {"color":"black","material":"leather"}
    llm_context = models.TextField()              # 챗봇 프롬프트용 요약
    released_at = models.DateField()              # 신상품 가중치 10%

features가 취향 벡터의 재료다. 색상·소재·실루엣·가격대를 여기에 넣고, 스코어링에서 코사인 유사도를 계산한다.

llm_context에 재고·할인을 넣지 않는다. 모델이 모르는 정보는 지어낼 재료조차 없다. 프롬프트 지시보다 데이터로 막는 게 강하다.

events — 가장 큰 테이블

python

class Event(models.Model):
    all_objects = models.Manager()              # Django 내부용 (먼저 정의)
    objects = VisitScopedManager()

    event_id = models.CharField(max_length=64, unique=True)   # 클라 생성, 멱등 키
    visit = models.ForeignKey(Visit, null=True, on_delete=models.CASCADE)
    event_type = models.CharField(max_length=32)
    scene_id = models.CharField(max_length=32, null=True)
    product_id = models.CharField(max_length=32, null=True)
    client_timestamp = models.DateTimeField()
    server_received_at = models.DateTimeField()
    metadata = models.JSONField(default=dict)   # dwell_ms, source, device

    class Meta:
        base_manager_name = "all_objects"
        indexes = [
            models.Index(fields=["visit", "client_timestamp"]),   # 워커
            models.Index(fields=["product_id", "event_type"]),    # /admin/products
            models.Index(fields=["scene_id", "event_type"]),      # /admin/scenes
        ]

visit이 null=True인 이유는 1년 후 익명화 때문이다. 연결만 끊고 집계용으로 남긴다.

scene_id/product_id를 metadata에 넣지 않고 최상위 컬럼으로 둔 것은 인덱스를 걸기 위해서다. 대시보드 집계가 전부 이 컬럼으로 돈다.

reports

python

class Report(models.Model):
    slug = models.CharField(max_length=16, unique=True, db_index=True,
                            default=lambda: secrets.token_urlsafe(9))
    visit = models.OneToOneField(Visit, on_delete=models.CASCADE)
    payload = models.JSONField(null=True)
    status = models.CharField(max_length=16, default="pending")
    attempt = models.IntegerField(default=0)
    created_at = models.DateTimeField(auto_now_add=True)

OneToOne이 한 방문에 한 리포트를 DB 레벨에서 보장한다. 워커가 병렬로 돌 때 남의 리포트에 덮어쓰는 사고를 막는다.

5. 인덱스 근거

인덱스는 추측이 아니라 실제 쿼리에서 역산한다.

쿼리발생 빈도인덱스
authenticate(token)모든 요청visits.token unique
start() 활성 visit 조회모든 진입visits(visitor, store, exited_at)
워커의 이벤트 로드방문당 1회events(visit, client_timestamp)
챗봇 히스토리 10턴대화 턴마다chat_logs(visit, created_at)
리포트 조회방문당 수회reports.slug unique
/admin/products 집계대시보드 열 때events(product_id, event_type)
배치 정리하루 1회visits(exited_at, entered_at) — 생략 가능

authenticate(token)이 가장 빈번한 쿼리다. unique 인덱스라 단건 조회로 끝나고, 이것이 JWT의 "DB 안 치기" 장점을 포기해도 되는 근거다.

6. JSONField를 쓸 곳과 안 쓸 곳

쓴다안 쓴다
events.metadata — 이벤트 타입마다 필드가 다름events.product_id — 집계에 인덱스 필요
products.features — 브랜드마다 속성이 다름products.price — 범위 검색
reports.payload — 리포트 구조가 자주 바뀜reports.status — 필터 조건
taste_profiles.vectortaste_profiles.character_type — 코호트 필터

기준은 "이걸로 WHERE/GROUP BY 하는가" 다. 한다면 컬럼, 안 하면 JSON.

8. 하지 말 것

① 벡터 DB / pgvector 도입

taste_profiles.vector를 JSONField에 넣고 파이썬에서 코사인 유사도를 계산한다. 매장 하나의 상품이 수십~수백 개라 전수 계산이 밀리초 단위로 끝난다. 벡터 검색 엔진은 수백만 건부터 의미가 있다.

② 이벤트를 별도 저장소(로그 파이프라인)로

Kafka·ClickHouse는 이 규모에 과하다. events 테이블 하나로 충분하고, 대시보드 집계는 5분 캐시로 커버된다.

③ 미리 파티셔닝

파티션 테이블은 마이그레이션·백업·인덱스 관리가 복잡해진다. 실제로 느려진 뒤에 해도 늦지 않다.

④ 소프트 삭제(is_deleted)

events·chat_logs는 append-only라 삭제 개념이 없고, 보존기간 만료는 진짜 삭제여야 한다. 개인정보를 "지웠다고 표시만" 하면 정책 위반이다.

9. 마이그레이션 순서

FK 의존을 따라간다.

bash

python manage.py makemigrations identity          # Visitor
python manage.py makemigrations stores            # Brand, Store, Scene, Product
python manage.py makemigrations visits            # → identity, stores
python manage.py makemigrations events chat       # → visits
python manage.py makemigrations analysis          # → visits, identity
python manage.py migrate

FK는 반드시 문자열로 참조한다("visits.Visit"). 클래스를 직접 import하면 app 간 순환 import가 생기고, 우리 의존 규칙이 코드 레벨에서 깨진다.
