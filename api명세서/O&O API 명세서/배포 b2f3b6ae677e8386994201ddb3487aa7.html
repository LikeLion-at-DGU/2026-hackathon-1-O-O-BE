배포

AWS 배포 계획 (1~2주)

이 프로젝트의 배포는 일반 Django와 두 가지가 다르다.
① SSE 스트리밍 때문에 ASGI + ALB 타임아웃 설정이 필요하고, ② Celery 워커가 별도 프로세스로 떠야 한다.
이 둘을 놓치면 로컬에서 되던 게 배포 후 안 된다.

2. 이 프로젝트의 함정 5개

① ALB idle timeout이 SSE를 끊는다

기본값 60초다. LLM 첫 토큰까지 시간이 걸리면 그 사이 데이터가 흐르지 않아 연결이 끊긴다.

bash

aws elbv2 modify-load-balancer-attributes \
  --load-balancer-arn <ARN> \
  --attributes Key=idle_timeout.timeout_seconds,Value=300

추가로 서버에서 하트비트를 보낸다.

python

# 첫 토큰 전까지 15초마다 주석 라인
yield ": keepalive\n\n"

SSE에서 :로 시작하는 줄은 주석이라 클라이언트가 무시한다. 연결만 살아 있게 한다.

② gunicorn 기본 설정으로는 스트리밍이 안 된다

bash

# ✗ 청크가 버퍼링되어 한 번에 나감
gunicorn config.wsgi

# ✓
uvicorn config.asgi:application --host 0.0.0.0 --port 8000 --workers 2

로컬 runserver에서는 되는데 배포하면 안 되는 대표 사례다. 배포 첫날 챗봇 스트리밍부터 확인한다.

③ 워커는 ALB 뒤에 없다

Celery 워커는 HTTP를 받지 않는다. 별도 프로세스로 띄우고, 죽으면 리포트가 영영 안 만들어진다. 헬스체크가 따로 필요하다.

bash

celery -A config inspect ping   # 응답 없으면 알림

④ 로그에 프롬프트를 찍지 않는다

CloudWatch에 LLM 요청/응답을 그대로 로깅하면 개인 발화가 로그에 영구 축적된다. privacy.mask_pii()로 DB를 지켜놓고 로그로 새면 의미가 없다.

python

logger.info("llm call", extra={"visit_id": visit.id, "tokens": n})   # ✓
logger.info(f"prompt:{prompt}")                                      # ✗

⑤ RDS 백업이 보존기간 정책을 무력화한다

chat_logs 90일 후 삭제 정책이 있는데, RDS 자동 백업이 35일치를 들고 있으면 삭제한 대화가 백업 안에 살아 있다.

백업 보존기간을 정책과 맞춘다.

RDS 백업 보존   7일    (운영 복구용 최소한)
chat_logs 보존  90일

7일이면 "삭제 후 최대 7일 안에 백업에서도 사라진다"가 성립한다.

yaml

# docker-compose.prod.yml
services:
  web:
    image: ${ECR_URI}:${TAG}
    command: uvicorn config.asgi:application --host 0.0.0.0 --port 8000 --workers 2
    env_file: .env
    ports: ["8000:8000"]
    restart: always

  worker:
    image: ${ECR_URI}:${TAG}
    command: celery -A config worker -Q analysis,image,batch -c 2 --loglevel=info
    env_file: .env
    restart: always

  beat:
    image: ${ECR_URI}:${TAG}
    command: celery -A config beat --loglevel=info
    env_file: .env
    restart: always

세 프로세스가 같은 이미지를 쓰고 명령어만 다르다. 배포가 한 번에 끝난다.

4. 시크릿 관리

.env 파일을 EC2에 직접 두지 않는다. SSM Parameter Store에 넣고 부팅 시 내려받는다.

bash

aws ssm put-parameter --name /oando/prod/OPENAI_API_KEY \
  --value "sk-..." --type SecureString

# 배포 스크립트에서
aws ssm get-parameters-by-path --path /oando/prod --with-decryption \
  --query "Parameters[*].[Name,Value]" --output text \
  | sed 's|/oando/prod/||' | tr '\t' '=' > .env

OPENAI_API_KEY가 새면 과금이 폭발한다. GitHub에 커밋되는 사고가 가장 흔하므로 .gitignore에 .env를 넣고, .env.example만 커밋한다.

5. 네트워크·보안 그룹

리소스인바운드

EC28000 ← ALB SG만

ElastiCache6379 ← EC2 SG만

RDS를 퍼블릭으로 열지 않는다. 로컬에서 접속이 필요하면 SSM Session Manager 포트포워딩을 쓴다.

bash

aws ssm start-session --target <instance-id> \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["<rds-endpoint>"],"portNumber":["5432"],"localPortNumber":["5432"]}'

SSH 키를 뿌리지 않아도 되고, 22번 포트를 아예 닫을 수 있다.

6. 정적 파일 · 이미지

S3 버킷
 ├── static/          Django collectstatic

CloudFront를 앞에 붙인다. 캐릭터 이미지는 16장 고정이라 캐시 적중률이 100%에 가깝다.

GET /stores/{key}/map도 CloudFront를 태울 수 있다. 응답에 개인정보가 없고 Cache-Control: public, max-age=60이라 안전하다. /enter는 POST라 캐시되지 않으니 신경 쓸 필요 없다.

7. CI/CD (GitHub Actions)

yaml

# .github/workflows/deploy.yml
name: deploy
on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_PASSWORD: test }
        options: >-
          --health-cmd pg_isready --health-interval 10s
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt
      - run: pytest

  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}   # OIDC. 키 저장 안 함
          aws-region: ap-northeast-2
      - uses: aws-actions/amazon-ecr-login@v2
      - run: |
          docker build -t $ECR_URI:$GITHUB_SHA .
          docker push $ECR_URI:$GITHUB_SHA
      - run: |
          aws ssm send-command \
            --instance-ids ${{ secrets.EC2_ID }} \
            --document-name "AWS-RunShellScript" \
            --parameters 'commands=[
              "cd /app",
              "export TAG='$GITHUB_SHA'",
              "docker compose -f docker-compose.prod.yml pull",
              "docker compose -f docker-compose.prod.yml run --rm web python manage.py migrate",
              "docker compose -f docker-compose.prod.yml up -d"
            ]'

AWS 액세스 키를 GitHub Secrets에 넣지 말고 OIDC를 쓴다. 키 유출 경로가 하나 사라진다.

마이그레이션은 web 컨테이너를 띄우기 전에 별도로 돌린다. 여러 컨테이너가 동시에 마이그레이션하면 충돌한다.

항목방법왜
워커 생존CloudWatch 알람 + celery inspect ping죽으면 리포트가 안 나옴

LLM 지연커스텀 메트릭3~4초를 넘어가면 UX 붕괴
5xx 비율ALB 메트릭
RDS 커넥션RDS 메트릭워커 + 웹이 커넥션을 나눠 씀

워커 생존 감시가 가장 중요하다. 웹은 죽으면 즉시 티가 나지만, 워커는 조용히 죽고 사용자는 "분석 중" 화면만 계속 본다.

python

# 간단한 자체 헬스체크 엔드포인트
def health(request):
    return JsonResponse({
        "db": check_db(),
        "redis": check_redis(),
        "worker": celery_app.control.ping(timeout=1) != [],
        "pending_reports": Report.objects.filter(status="pending").count(),
    })

pending_reports가 계속 쌓이면 워커 문제다.

10. 프론트엔드가 정해지면

별도 배포(Vercel 등)라면 CORS 설정이 필요하다.

python

CORS_ALLOWED_ORIGINS = ["https://oando.vercel.app"]
CORS_ALLOW_HEADERS = [*default_headers, "x-visit-token", "x-anonymous-uuid"]

커스텀 헤더를 CORS_ALLOW_HEADERS에 넣지 않으면 preflight에서 막힌다. 이걸 빼먹어서 "왜 로컬은 되는데 배포하면 401이지"로 하루를 쓰는 경우가 흔하다.

Django가 같이 서빙한다면 빌드 결과물을 staticfiles에 넣고 SPA 라우팅용 catch-all을 둔다. 배포 대상이 하나라 단순하지만, 프론트 수정 때마다 백엔드까지 재배포된다.

QR이 매장에서 스캔되므로 HTTPS가 필수다. 카메라·클립보드 API가 HTTP에서 동작하지 않고, 브라우저가 경고를 띄운다. ACM 인증서는 무료다.
