1. 충돌 — 양쪽이 다르게 정의

① visit_token 형식

팀 명세서모듈 문서
형식JWT (eyJhbGci...)불투명 랜덤 43자
만료exp 내장없음 (exited_at IS NULL로 판단)
검증서명 + DB 조회DB 조회 1회
폐기불가DB 한 줄

근거: 공통 규약이 이미 "매 요청 DB 조회(stateless)"다. JWT의 유일한 장점인 무상태 검증을 스스로 포기한 상태라 비용만 남는다. 게다가 exp 만료가 붙으면 장시간 체류자의 후반 데이터가 통째로 유실된다.

인터페이스(X-Visit-Token, 401 INVALID_VISIT_TOKEN)는 그대로 유지되므로 클라이언트 변경은 없다.

② 식별자 3중 노출 — /events

팀 명세서 /events는 세 가지를 동시에 요구한다.

X-Visit-Token: <토큰>        ← 필수
X-Anonymous-UUID: <uuid>     ← 필수
{ "visit_id": "v_9f8e...",   ← body에도
  "events": [...] }

셋 다 같은 사실을 가리킨다. 토큰 하나면 visit이 확정되고, visit.visitor로 uuid까지 도달한다.

불일치 시 동작이 정의돼 있지 않다.

X-Visit-Token: <v_AAAA의 토큰>
{ "visit_id": "v_BBBB" }      ← 어느 쪽이 이기나? 403? 무시?

토큰을 도입한 목적이 visit_id 위조 주입 차단인데, visit_id를 계속 받으면 방어가 무의미해진다.

제안: 토큰만. /chat, /finish도 동일.

③ /finish 경로

팀 명세서모듈 문서
POST /visits/{visit_id}/finishPOST /finish

URL에 visit_id가 박히면 서버 로그·리퍼러·브라우저 히스토리에 남는다. 토큰이 이미 visit을 지시하므로 경로 파라미터가 불필요하다.

④ store_token vs store_key

json

"store_token": "mcm-seongsu-001"     ← 서명도 만료도 없는 평문 slug

이름은 토큰인데 값은 slug이고, 검증 규칙이 없다. 그런데 에러 목록에 401(만료) 이 있다.

진입 관문에서 401이 나면 그 사용자의 데이터가 하나도 남지 않는다. 존재 확인만 하고 통과시키는 쪽을 권하며, 그렇다면 이름도 store_key가 맞다.

⑤ anonymous_uuid 반환 조건

팀 명세서모듈 문서
"신규 발급 시 포함" (조건부)항상 반환 + is_new 플래그

클라이언트가 죽은 uuid를 보냈을 때 서버는 새로 발급하지만, 응답에 없으면 클라이언트는 자기 uuid가 여전히 유효하다고 오해한다. 영영 죽은 uuid를 계속 보내게 된다.

⑥ /enter 응답에 상품 인라인

팀 명세서모듈 문서
scenes[].products 인라인씬만, 상품은 GET /scenes/{id}

초기 응답 크기와 캐시 입도 때문이다. 다만 scene_view 이벤트가 이미 있어 "어느 씬을 봤는지"는 별도로 잡히므로, 이건 논의 대상이지 우리 안이 명백히 맞는 건 아니다.

⑦ ID 형식

팀 명세서모듈 문서
"v_9f8e", "p_101", "sc_01" 문자열정수 PK

팀 명세서가 맞다. 순번 열거를 막고, 로그에서 타입이 즉시 구분된다. 모듈 문서의 정수 PK를 문자열로 고쳐야 한다.

⑧ entry_channel

팀 명세서모듈 문서
web / signage / link삭제

개인 폰 전제라면 값이 web 하나로 고정된다. 다만 아래 5-③ 참고 — /admin이 channel 필터를 쓰고 있어 단순 삭제로는 끝나지 않는다.

⑨ 응답 코드 /enter

200(팀) vs 201(우리). visit을 새로 만들면 201, 재사용이면 200이 정확하다. 사소하다.

2. 팀 명세서에만 있음 — 채택할 것

① event_id 멱등 + 202 { accepted, duplicated }

json

{ "accepted": 2, "duplicated": 0 }

클라이언트가 재전송했을 때 몇 건이 중복이었는지 알려준다. 배치 전송 신뢰성 확보에 필요하다. 모듈 문서에 없다.

② client_timestamp + server_received_at 이중 저장

클라이언트 시계는 틀어질 수 있고, 배치 전송이라 도착 시각과 발생 시각이 다르다. 둘 다 저장해야 체류시간 계산이 가능하다.

Postman 컬렉션의 at 단일 필드는 잘못됐다. 수정 필요.

③ scene_id / product_id를 최상위 필드로 ⇒( 매대별 상품정보 or 상품 전체 넘버링)

json

{ "event_type": "product_dwell", "product_id": "p_101",
  "metadata": { "dwell_ms": 30000 } }

metadata 안에 묻지 않고 최상위에 둔다. 인덱스를 걸 수 있어 집계 쿼리가 빨라진다. Postman의 target_id보다 명확하다.

④ 리포트 payload 스키마

모듈 문서엔 payload가 JSONField라고만 돼 있다. 팀 명세서가 훨씬 구체적이다.

json

{
  "status": "ready",
  "character": { "type_code": "CLBM", "name": "클래식 미니멀리스트",
                 "one_liner": "절제된 무드를 즐기는 타입" },
  "top_keywords": ["블랙", "레더", "미니멀"],
  "interested": [...],
  "recommendations": [{ "product_id": "p_204", "reason": "선호 소재(레더) 일치",
                        "score": 0.87 }],
  "confidence": 0.62,
  "visit_summary": { "scenes_viewed": 4, "products_viewed": 9, "questions": 3 }
}

recommendations[].reason이 특히 중요하다. 추천 순위를 계산으로 뽑아야 하는 이유가 여기 있다 — LLM에 맡기면 이 근거를 만들어낼 수 없다.

type_code: "CLBM" 4글자는 4축 조합을 뜻한다. 모듈 문서의 character.axes와 맞는다.

⑤ /admin 세부 엔드포인트 5종

모듈 문서는 summary() / by_product() 2개로 추상화했는데, 팀 명세서가 훨씬 구체적이다.

Endpoint내용
GET /admin/funnelVisit 수, 재방문, 평균 체류, 진입률, 전환율, 리포트 완료율
GET /admin/products상품별 조회·체류·저장·추천클릭
GET /admin/scenes전시존별 유입·체류·핫스팟·전환
GET /admin/cohorts색상·소재·실루엣·가격대 분포, 16유형별 선호
GET /admin/chat-insights챗봇 질문 주제·구매 망설임 요인·전환

"리포트 완료율" 지표가 이탈자 추적을 전제한다. 모듈 문서의 is_auto_closed가 정확히 이 지표의 분모를 만든다.

⑥ visit_summary의 "이전 대비 변화" ⇒ 재방문율 파악 , 서비스를 나갔을때 다시 돌아 올 수 있게 하는 장치로 설정 ⇒ 재방률은 우리 판단에서 배제

재방문자의 직전 방문과 비교한다는 뜻이다. TasteProfile을 visit이 아니라 visitor에 매단 모듈 설계와 정확히 맞물린다.

⑦ PII 마스킹 · 보존기간

/chat에 "마스킹·보존기간 대상"으로 언급돼 있다. 모듈 문서엔 오히려 "원문 그대로 저장"이라고 반대로 적혀 있어 수정이 필요하다. privacy 모듈 미작성.

4. 양쪽 다 비어 있음 — 새로 정해야

① 이미지 생성이 명세 어디에도 없다

리포트 payload 스키마에 image_url이 없고, /finish·/reports 설명에도 이미지 언급이 없다. 5장 AI 활용에도 "리포트·데이터 생성"까지만 적혀 있다.

세션에서 계속 논의한 캐릭터 이미지가 팀 명세서에 아직 반영되지 않은 상태다. 기획에 있는데 명세에만 빠진 건지, 스코프 밖인지 확인이 필요하다.

② SSE 스트리밍 중 에러

data: {"delta": "이 제품은 "}
[OpenAI 타임아웃]              ← 이미 200 헤더가 나갔다. 어떻게 알리나?

400/401/429는 스트림 시작 전에만 유효하다. 스트림 안에서 알리는 규약이 필요하다.

data: {"error": {"code": "LLM_TIMEOUT"}}
data: {"done": true, "message_id": "m_55", "is_partial": true}

③ 챗봇 이벤트를 누가 만드나

chatbot_open, question_submit, recommendation_impression, recommendation_click이 이벤트 타입에 있는데, /chat 명세엔 chat_logs만 적혀 있다.

question_submit은 /chat 호출과 1:1이므로 서버 자동 생성이 맞다. 클라이언트가 둘 다 부르면 누락·중복이 생긴다.

④ hotspot_click의 대상 정의

이벤트 타입에는 있는데 /enter 응답 예시에 핫스팟이 없다. Response 표에는 "상품/핫스팟"이라고 적혀 있어 표와 예시가 어긋난다.

씬 사진 위에 점을 찍는 UI인지, 상품 리스트인지에 따라 갈린다. 후자면 이벤트 타입을 지우는 게 낫다.

⑤ 배치 전송 제약

한 요청에 이벤트 몇 개까지? 순서 보장? 재전송 윈도우? 정의가 없다.

5. 새로 발견한 자기모순 3개

① /events — "유실 방지"인데 실제로는 유실된다

설명: "브라우저가 닫혀도 직전 구간 유실 방지"

그런데 인증이 X-Visit-Token 필수다. 사용자가 /finish로 종료한 뒤 클라이언트가 마지막 배치를 보내면,

python

authenticate(token)  →  exited_at IS NOT NULL  →  401

마지막 구간이 정확히 유실된다. 종료 직전 구간이 전환 분석에서 가장 중요한데 그 부분이 날아간다.

해결안 두 가지

  • 종료 후 10분 유예 — /events만 닫힌 visit도 허용하고, entered_at ~ exited_at 범위 밖 이벤트는 표시
  • /finish 호출 전에 flush 강제 — 클라이언트 책임이 커지고 누락 위험

전자를 권한다. authenticate()에 grace 옵션을 두면 된다.

python

def authenticate(token, grace=timedelta(0)) -> Visit:
    ...filter(Q(exited_at__isnull=True) | Q(exited_at__gt=now() - grace))

② /admin의 channel 필터 ↔ entry_channel 삭제

/admin/* 공통 쿼리 파라미터에 channel 이 있다. entry_channel을 지우면 이 필터가 죽는다.

entry_channel 삭제 결정은 유지하되, 채널 판정을 서버로 옮겨야 필터가 살아난다.

python

class EntryPoint(models.Model):
    key = models.SlugField(unique=True)      # QR에 담기는 값
    store = models.ForeignKey(Store, ...)    # 매장은 하나
    channel = models.CharField(...)          # entrance / signage / link

클라이언트는 아무것도 보내지 않고, 서버가 store_key로 판정한다. 위조 불가능하고 "어느 QR이 잘 먹히나"까지 알 수 있다.

즉 entry_channel 필드는 삭제하되, 채널 개념 자체는 살려야 한다. 앞선 "그냥 삭제" 결론을 이 지점에서 보정한다. ⇒ 그러면 admin에 채널 판정을 삭제하면 되지 않을까

③ Notion 페이지 상태

/enter를 제외한 5개 엔드포인트 페이지가 휴지통 상태로 조회된다. 명세서 (1) 본문에서는 여전히 참조 중이다. 구버전 정리 중 실수인지 확인이 필요하다.

6. 조치 우선순위

팀 합의가 먼저 필요한 것 (다른 결정이 여기에 물림)

  1. visit_token 형식 — JWT vs 불투명
  1. 식별자 노출 — visit_id를 계속 받을지
  1. 이미지 생성 스코프 포함 여부

합의 없이 바로 고칠 수 있는 것 (우리 문서 수정)

  1. ID를 문자열로 (v_, p_, sc_ prefix)
  1. client_timestamp + server_received_at — Postman 컬렉션 포함
  1. 리포트 payload 스키마를 팀 명세서 기준으로
  1. /admin 5종 엔드포인트로 세분화
  1. PII 마스킹 — privacy 모듈 신규 작성

팀에 제안할 것

  1. is_resumed, 24시간 배치, is_auto_closed
  1. /events 유예 시간 (자기모순 ①)
  1. EntryPoint 테이블 (자기모순 ②)
  1. 씬 좌표 + GET /stores/{key}/map
