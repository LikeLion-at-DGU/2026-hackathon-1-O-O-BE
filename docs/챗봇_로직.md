# 챗봇 로직 (뮤즈 · 트리거 중심)

기획 방향: **고객을 뮤즈로 만들고, 뮤즈가 되는 여정을 서비스로 녹인다.**
그 여정의 실체는 **추상(색·기분·분위기) → 구체(물건·진열대 번호)** 변환이다.

작성 2026-08-13 · 관련: [`필드_가이드.md`](필드_가이드.md) · [`../기획.md`](../기획.md) · [`../tasks/결정사항.md`](../tasks/결정사항.md)

## 0. 전체 흐름

```
입장
 └ 인사 말풍선 (서버가 chat_logs에 적립)

탐색 ─ 클릭이 말풍선으로 쌓임 (진열대·상품·프리셋)
      행동은 /events로 별도 수집
        │
        ├─ 트리거 조건 충족 → 🐻 관찰 + 확인 질문 [맞아요][아니에요]
        │       맞아요 → 축 반영 + 즉시 상품 3개 + 진열대 번호
        │       아니에요 → 감점 + "그렇다면 뮤즈님의 ○○는?" → 채팅 유도
        │
        └─ "채팅으로 대화하기" → LLM 챗봇 (문맥 자동 조립)

퇴장 → 워커가 축 확정 → 리포트(뮤즈 프로필)
```

**묻기 전에 관찰하고, 관찰한 것을 확인받고, 확인받은 즉시 물건으로 답한다.**

## 1. 설계 축 3개

**① 트리거 중심 — 대놓고 묻지 않는다.**
"좋아하는 색이 뭐예요?"는 설문이고, "블랙 위주로 보셨네요, 색은 이쪽이 편하세요?"는 대화다. 매장에서 서 있는 사람에게 타이핑을 요구하지 않고 버튼 한 번으로 끝낸다.

**② 축이 아니라 상품을 묻는다.**
상품 하나에 8개 축이 붙어 있어서 "이 백팩 마음에 드세요?" 한 번이 축 8개를 가져온다. 손님에게도 "Y2K 무드를 좋아하나요?"보다 답하기 쉽다.

**③ 대비가 정보다.**
절대 점수가 아니라 **관심 상품들의 공통점**에서 취향을 뽑는다. 다 좋아하는 사람은 취향이 없는 것이고, 그걸 억지로 유형에 밀어넣지 않는다.

## 2. 유지되는 기존 골격 (구현 완료)

```
chat_logs        클릭이 말풍선으로 쌓이는 타임라인, role 4종
프리셋 3버튼      가격·재질·디자인 의도 (LLM 아님, 즉시·무료)
채팅으로 대화하기  문맥 자동 조립 → 상품명 없이 질문 가능
/events          행동 원본, append-only, 멱등
```

트리거 로직은 이 위에 얹는다. **기존 흐름을 바꾸지 않는다.**

## 3. 트리거 4군

### 1군 · 상품 확인 (주력)

| 조건 | 문장 | 결과 |
| --- | --- | --- |
| 같은 상품 재조회 2회+ | "Stark 백팩에 다시 돌아오셨네요. 마음에 남으셨어요?" | 관심 상품 집합 추가 |
| 한 상품 체류 30초+ | "Aren 토트를 오래 보고 계세요. 이런 쪽이 끌리시나요?" | 동일 |

찜은 기획에서 빠졌다. 예전에는 "찜 = 묻지 않고 즉시 집합 추가"였는데, 그 자리를
`맞아요`로 확인한 상품(`confirmed`)이 대신한다 — 손님이 직접 답한 것이라 더 강한 신호다.

### 2군 · 대비 2택

왕복 조회(A→B→A) 감지 시 **항상 발동**한다.

```
🐻 두 개를 견주고 계시네요. 어느 쪽이 더 끌리세요?
   [ Classic 토트 ]   [ Stark 백팩 ]
```

| 두 상품의 축 차이 | 처리 |
| --- | --- |
| **≤ 3개** | 귀속 가능 → 우선순위 1위 차이 축 **lock** |
| **4개 이상** | 귀속 불가 → 승자만 집합 추가, lock 없음 |

차이 축 우선순위 = 손님이 먼저 인지하는 순서: `color > mood > material > pattern > silhouette > use_case`

> 시드로 재보니 8축 중 1~2개만 다른 쌍은 **3%뿐**이었다(28쌍 중 1쌍). 게이트를 걸면 죽은 트리거가 되므로 **발동은 항상 하고 점수 처리만 나눈다.**

### 3군 · 축 확인 (확정타)

7개 조건을 **전부** 충족해야 발동한다. 관찰 트리거 중 유일하게 `lock`을 준다.

```
① 체류 5초 이상 조회가 5개 이상
② 해당 축의 특정 값이 그중 60% 이상            ← 개수 아니라 비율
③ 서로 다른 진열대 2곳 이상에서 나타남          ← 동선 오탐 방어
④ 같은 축의 **2등 값**이 1개 이하              ← 아래 참고
⑤ 손님이 `맞아요` 한 상품이 그 축 값을 갖거나, 조회 쏠림 80% 이상
⑥ 16유형 4축 중 아직 lock 안 된 축
⑦ 방문당 1회 (예산 예약)
```

③이 결정적이다. 전시존이 무드로 나뉘어 있어서(`sc_03` = Y2K) **한 진열대만 둘러봐도 같은 무드 3개가 자동으로 걸린다.** 그건 취향이 아니라 동선이다.

**④를 "다른 값 총합 1개 이하"로 두면 ②와 충돌한다** — 5개 중 3개(60%)면 나머지가 2개라 항상 탈락하고, 실질 임계가 80%가 되어 ②가 무의미해진다. 원래 의도가 "한쪽으로 쏠렸는가"이므로 2등 값의 개수를 본다.

**⑤를 축값 0.7 이상으로 두면 발동 불가다** — shrinkage 때문에 집합이 5개 전부 같은 값이어야 0.71이 된다. 축값은 표본을 눌러주는 장치이지 "확인을 받았는가"를 재는 값이 아니다. 그래서 `confirmed` 상품을 직접 본다.

대상 축은 `mood` · `color` · `material` · `pattern` 넷이다.
제외: `price_band`(예산을 대놓고 묻는 셈), `category`(자명), `silhouette`(손님이 인지하기 어려움)

```
🐻 진열대를 옮겨가면서도 블랙 위주로 보셨네요. 색은 이쪽이 편하세요?
```

"진열대를 옮겨가면서도"를 넣어 **판단 근거를 문장에 드러낸다.**

### 4군 · 회피형 (부정 신호)

```
조건: 그 존에 scene_view가 있고, 그 존의 다른 상품은 열었는데
      특정 축 상품만 조회 0건
```

같은 조건에서의 선택이어야 회피가 성립한다. `/enter`가 전체 목록을 내려주므로 "목록에 있었다"만으로는 판정할 수 없다.

```
🐻 화려한 색은 눈에 안 들어오시는 것 같아요. 차분한 쪽이 편하세요?
```

`맞아요` → **그 값의 회피율을 1.0으로 확정**한다. 반대 진영에 따로 가산하지 않는다 — 축값이 비율이라 한쪽이 내려가면 **반대쪽 진영 격차가 자동으로 벌어진다.** 절대값 체계였을 때 필요했던 "반대 축 +0.7"은 삭제했다.

### 트리거 평가 순서 (구현)

```
2군 대비 → 1군 상품 확인 → 3군 축 확인(예약) → 4군 회피 → 특수(취향 변화·빠른 훑기)
```

**2군이 1군보다 먼저다.** 왕복 조회(A→B→A)는 재조회를 포함하므로 1군을 앞에 두면 항상 1군이 먹고 2군은 영원히 발동하지 않는다(도달 불가 코드가 된다).

### 특수 · 빠른 훑기 구제

```
조건: 상품 4개 이상 조회 + 전부 체류 5초 미만
```

```
🐻 찾으시는 게 있으세요?
   [ 매일 쓸 것 ]  [ 특별한 날 ]  [ 그냥 둘러봐요 ]
```

**선택지는 반드시 8축의 진영이어야 한다.** 처음에 "큰 가방 / 작은 가방"으로 뒀는데, **크기는 우리 8축에 없는 개념**이라 답이 들어갈 자리가 없었다. `category`로 억지 매핑하면 16유형에도 기여하지 못한다.

`use_case`를 고른 이유:

| 후보 축 | 즉답 가능? | 16유형 4축? | 판단 |
| --- | --- | --- | --- |
| `use_case` (D/S) | ✅ 매장에 온 목적과 직결 | ✅ | **채택** |
| `mood` (C/T) | △ 훑는 중인 사람에겐 아직 모호 | ✅ | 후순위 |
| `color` (N/V) | ✅ 하지만 값이 9개라 버튼 부적합 | ✅ | 탈락 |
| `category` | ✅ 하지만 자명하고 4축 아님 | ❌ | 탈락 |

`매일 쓸 것`(daily·work) / `특별한 날`(travel·going_out)은 **`use_case` 진영과 1:1**이라 `lock`을 줄 수 있다. 크기 같은 축 밖 개념은 lock이 불가능하다.

답을 받으면 그 진영으로 추천 3개를 내고, 손님이 하나를 열면 그때부터 정상 트리거 사이클로 들어온다. 크기는 추천 단계에서 자연히 좁혀진다(출근용 → 노트북 들어가는 토트·백팩).

`그냥 둘러봐요` → 그 방문 전체 확인 중단. **출구가 없으면 질문이 압박이 된다.**

### 특수 · 취향 변화 재질문

```
조건: lock된 축의 반대 진영에 조회 3개 + 그중 `맞아요`로 확인한 상품 1개 이상
```

```
🐻 아까는 절제된 쪽이라고 하셨는데, 지금은 눈에 띄는 쪽을 보고 계세요.
   마음이 바뀌셨나요?              [ 바뀌었어요 ]  [ 그대로예요 ]
```

`같은 축 1회` 제한의 유일한 예외다.

### 손님용 어휘 (트리거 문구의 단일 출처)

내부 축 값을 그대로 말하면 안 된다. `y2k_street`·`실루엣`은 분류 용어다.
구현 위치: `apps/chat/wording.py` 상수. **`TextChoices`의 label은 건드리지 않는다** — Admin 상품 목록과 시드 검수가 그 label을 쓴다.

| 내부 값 | 손님에게 |
| --- | --- |
| `minimal` | 절제된 느낌 |
| `bold_statement` | 눈에 띄는 느낌 |
| `classic_heritage` | 클래식한 느낌 |
| `y2k_street` | 스트리트한 느낌 |
| `coated_canvas` | 생활 방수 되는 소재 |
| `grained_leather` | 스크래치에 강한 가죽 |
| `smooth_leather` | 매끄러운 가죽 |
| `nylon` | 가벼운 나일론 |
| `visetos_monogram` | 패턴이 있는 쪽 |
| `solid` | 무지 |
| `studded` | 스터드가 있는 쪽 |
| `structured` | 형태가 잡힌 |
| `slouchy` | 부드럽게 흐르는 |
| N진영(black·white·beige·navy) | 차분한 색 |
| V진영(red·pink·metallic·visetos_mix) | 눈에 띄는 색 |
| D진영(daily·work) | 매일 쓸 것 |
| S진영(travel·going_out) | 특별한 날 |

**브랜드 고유명(비세토스 등)은 손님이 아는 경우가 있어 병기해도 된다.** 다만 트리거 문장은 짧아야 하므로 기본은 위 표를 쓰고, 상품 상세의 `attributes`가 정식 명칭을 이미 보여준다.

> **관찰 코멘트(버튼 없는 서사용 멘트)는 넣지 않는다.** 데이터 값이 0인데 예산 관리만 복잡해지고, 위 문장들이 이미 관찰을 담고 있다.

## 4. 분기 처리

### `맞아요`
집합에 추가하거나 축을 lock한 뒤 **즉시 물건으로 착지**한다.

```
🐻 그럼 이런 것도 보실래요?
   [카드] Nylon 백팩    2번 진열대 2번
   [카드] Classic 토트   3번 진열대 1번
```

축 확인이면 완성도 점프를 보여준다 — "뮤즈 프로필이 42% → 68%로 채워졌어요."
**확인의 대가로 새 물건을 받아야** 손님이 왜 답했는지 안다.

### `아니에요` — 트리거 종류에 따라 다르다

**상품 확인(1군)의 `아니에요`** — 그 상품을 관심 상품 집합에서 **제외**한다(재조회·체류로 이미 들어갔다면 빼낸다). 다시 본 이유가 좋아서가 아니라 **확신이 안 서서**일 수 있기 때문이다.

```
🐻 그러셨군요. 무엇이 걸리세요?        [ 채팅으로 대화하기 → ]
```

**축 확인(3군)·회피형(4군)의 `아니에요`** — 가설 축에 감점하고 그 축은 이번 방문에 다시 묻지 않는다.

```
🐻 그렇다면 뮤즈님의 무드는 어떤 것인지 알려주실 수 있나요?
                                    [ 채팅으로 대화하기 → ]
```

발화에서 같은 축의 다른 값이 나오면 **그건 lock**이다. **틀린 가설이 오히려 정확한 답을 끌어낸다.**

### 무응답
보류. 상품 2개를 더 보면 지나간 것으로 처리하고 강제하지 않는다.

### 발화 축을 되돌려 확인했는데 `다시 고를래요`

**카드를 9개 나열하지 않는다.** 매장에서 서서 고르기에 부담이고, 색 9개·소재 6개를 늘어놓으면 설문이 된다.

어긋난 축 **하나만 진영 2택**으로 되묻는다.

```
🐻 색부터 다시 볼게요. 어느 쪽이 가까우세요?
   [ 차분한 색 ]   [ 눈에 띄는 색 ]
```

추출된 축이 여러 개면 **우선순위 1위 축**(color > mood > material > pattern)만 되묻고 나머지는 버린다. 손님이 이미 "아니다"라고 했으므로 전부 다시 확인받을 필요가 없다.

### 발화에서 축이 안 잡히면
"못 알아들었어요" 대신 **2택으로 되돌린다.**

```
🐻 지금까지 보신 것 중 어느 쪽이 더 가까운가요?
   [ Classic 토트 ]  [ Stark 백팩 ]
```

**항상 저비용 선택지로 회귀하는 게 안전망이다.**

## 5. 점수 체계

### 관심 상품 집합

```
진입:  체류 20초+ · 재조회 2회+ · 상품 확인 `맞아요`
```

질문 트리거(30초)보다 집합 진입(20초)이 낮은 건 의도다. **질문은 더 강한 신호일 때만** 던지고 데이터는 더 넓게 모은다.

### 축값

```
축값 = (집합 내 그 값의 비율 × n/(n+2)) − 회피율        범위 [-1, 1]
                                    n = 집합 크기
```

**비율인 이유**: 여러 상품의 공통점이 곧 취향이다. 관심 상품 3개가 전부 블랙이면 색 취향이고, 3개가 다 다르면 색은 안 가리는 것이다.

**`n/(n+2)`인 이유**: 비율만 쓰면 표본 1개가 1.0이 되어 8개 중 5개(0.625)를 이긴다.

| 집합 | 비율 | 보정 후 |
| --- | --- | --- |
| 1개 중 1개 | 1.0 | 0.33 |
| 3개 중 3개 | 1.0 | 0.60 |
| 8개 중 5개 | 0.625 | 0.50 |

**회피율도 비율**로 통일한다 — `(노출됐지만 조회 0인 수) / (노출된 수)`. 절대값 감점을 섞으면 어떤 비율도 한 번에 뒤집힌다.

### 축 유효성 — 진영 격차로 판정

```
유효성 = |진영A 합 − 진영B 합| ≥ 0.25      (보정 전 비율로 계산)
         AND 집합 크기 ≥ 3                 (lock이면 면제)
```

**최소 집합 크기가 필요하다.** 유효성은 비율만 보므로 집합이 1개면 그 축은 항상 격차 1.0이 되어 **상품 하나로 4축이 전부 확정**된다. shrinkage는 축값만 누르고 유효성 판정에는 관여하지 않는다.

값 단위(`top1 − top2`)로 보면 틀린다.

```
black 0.3 · navy 0.3 · pink 0.3
  값 단위 :  0.3 − 0.3 = 0        → "색 취향 없음" (틀림)
  진영 단위:  N(0.6) − V(0.3) = 0.3 → N진영 (맞음)
```

16유형은 **진영 대결**이므로 유효성도 진영으로 본다.
**사용 단위는 분리한다** — 유효성은 진영, 추천 스코어링은 값.

### 무효 축

```
16유형        판정 보류 → 인접 유형 함께 제시
추천          가중치 0
confidence    기여 안 함
```

**억지로 유형을 붙이지 않는다.** 기획의 "confidence 낮으면 탐색 중 표시"와 맞물린다.

### lock

```
대상:  축 확인 `맞아요` · 자유 발화로 직접 말한 축 · 2택(차이 ≤3개) 승자
값:    1.0, 격차 검사 면제
효과:  행동 기여 무시 (취향 변화 재질문만 예외)
```

lock은 **손님이 축을 특정해서 답한 경우만**. 상품 단위 긍정은 귀속이 불명확하다.

## 6. 예산·쿨다운

```
확인형 총 3회
  ├─ 상품·대비·회피   최대 2회
  └─ 축 확인          1회 예약  ← 다른 군이 못 씀

워밍업          상품 3개 조회 + 입장 후 60초
확인 사이 간격   상품 2개 조회 이상
같은 축 재질문   1회 (취향 변화만 예외)
`그냥 둘러봐요`  그 방문 전체 중단
```

축 확인을 예약하지 않으면 1군이 예산을 먹어서 **lock을 주는 유일한 관찰 트리거가 실제로 안 나간다.**

## 7. 저장 (스키마 변경 0)

**축값은 누적이 아니라 함수다.**

```
축값 = f(관심 상품 집합, 회피 데이터)
```

같은 입력에서 항상 같은 결과가 나오므로 **저장할 필요가 없다.** 방문 중 표시할 때도, 퇴장 후 워커가 확정할 때도 같은 함수를 돌린다. **행동 점수 이중 계산 문제가 구조적으로 사라진다.**

저장하는 것은 `events`에 없는 것들뿐이다.

**구현에서 확정한 것**: `pending_action`을 파생 계산만으로는 복원할 수 없다. 응답(`맞아요`)이 왔을 때 그게 어느 축·어느 상품을 물은 가설이었는지 알아야 하는데 `chat_logs`에는 문구만 남는다. 그래서 `pending`도 함께 저장한다(같은 JSONField 안이므로 마이그레이션은 여전히 0).

```json
TasteProfile.vector = {
  "pending": { "message_id": "m_30", "kind": "axis_confirm", "axis": "mood",
               "value": "classic_heritage", "products": [], "options": [...] },
  "locks":  { "color": "black", "mood": "y2k_street" },
  "spoken": { "material": "grained_leather" },
  "asked":  ["color", "mood"],
  "confirm_count": 2
}
```

`chat_logs`에 문구만 남으면 "어느 축을 물었는지" 파싱이 취약해서 명시 저장한다. JSONField라 마이그레이션이 없다.

## 8. 실패·경계 처리

| 상황 | 동작 |
| --- | --- |
| 트리거가 하나도 안 걸림 | 정상. 유효 축이 적어 confidence 낮음 → "탐색 중" |
| 조건에 맞는 상품 0개 | 솔직히 말하고 가장 가까운 1개. "정확히 맞는 게 없어요. 대신 결이 비슷한 건…" |
| LLM 실패·429 | **카드·프리셋·트리거는 계속 동작** → 서비스가 멈추지 않는다 |
| 재고·할인 질문 | 단정 금지, 매장 직원 안내 |

**트리거 → 확인 → 추천까지가 LLM 없이 완결된다.** 자유 발화만 LLM을 타므로 데모 중 OpenAI가 죽어도 핵심 경험이 살아 있다.

## 9. 리포트 연결

```
당신이 확인해준 것        좌표                       당신의 물건
"블랙이 편해요"      →   color: black (lock)    →   Classic 토트
"스트리트한 결"      →   mood: y2k (lock)       →   + 스터드 키링
색을 안 가리셨어요    →   color 판정 보류         →   (인접 유형 함께)
```

- **뮤즈 아키타입** = 16유형 (계산 그대로, 이름만 호명형)
- **뮤즈 프로필 완성도** = `confidence`와 **같은 값**이다. API 응답 필드명만 `profile_completion`이고 계산은 하나다 (유효 축 개수 + lock 개수 + 집합 크기). 두 개를 따로 계산하면 화면과 리포트의 숫자가 어긋난다
- **말과 손이 달랐던 지점** = 발화 축 vs 집합 비율 불일치
- **가설 적중률** = 맞아요/아니에요 비율 → 브랜드에 "우리가 고객을 얼마나 정확히 읽는가"

마지막 항목이 B2B 자산이다. 구매 로그에는 남지 않는 데이터다.

## 10. API 명세 변경 (두 문서)

### 채팅 액션 메시지 기록 — `POST·GET /chat/messages`

**요청 `type`에 3개 추가** (API 입력 enum이라 마이그레이션 없음)

| 값 | 언제 | 함께 보내는 것 |
| --- | --- | --- |
| `hypothesis_yes` | `맞아요` | `reply_to`(가설 message_id) |
| `hypothesis_no` | `아니에요` | `reply_to` |
| `choice` | 2택·구제 트리거 선택 | `reply_to` + `product_id` 또는 `option` |

**POST 응답 확장** — 서버가 방금 만든 후속 말풍선과 추천을 함께 돌려준다(왕복 1회).

```json
{
  "messages": [ { "message_id": "m_31", "role": "assistant",
                  "content": "그럼 이런 것도 보실래요?" } ],
  "recommendations": [ { "product_id": "p_302", "name": "Nylon 백팩",
                         "thumbnail": "...", "scene_no": 2, "product_no": 2,
                         "reason": "블랙·데일리와 일치" } ],
  "profile_completion": 0.68
}
```

**GET 응답에 `pending_action` 추가** — 화면 복원 시 버튼을 다시 그려야 한다.

```json
{
  "messages": [ ... ],
  "current_context": { "scene_id": "sc_01", "product_id": "p_101" },
  "pending_action": {
    "kind": "hypothesis",
    "reply_to": "m_30",
    "options": [ { "label": "맞아요", "type": "hypothesis_yes" },
                 { "label": "아니에요", "type": "hypothesis_no" } ]
  }
}
```

`pending_action`은 **저장하지 않고 파생 계산**한다 — 마지막 assistant 메시지가 가설이고 아직 응답이 없으면 생성. `TasteProfile.asked`로 어느 축인지 복원한다.

### 컨텍스트 챗봇 — `POST /chat`

**요청은 변경 없음.** 응답 `done` 이벤트만 확장한다.

```
data: {"done": true, "message_id": "m_55",
       "recommendations": [ { "product_id": "p_204", "name": "Stark 백팩",
                              "thumbnail": "...", "scene_no": 3, "product_no": 2,
                              "reason": "선호 소재(레더)와 일치" } ],
       "extracted": { "axes": { "color": "beige", "mood": "minimal" },
                      "needs_confirm": true },
       "profile_completion": 0.55}
```

- `recommendations`에 **`scene_no`·`product_no` 추가** — 카드와 답변 문장이 같은 번호를 가리켜야 한다
- `extracted` 신규 — 발화에서 뽑은 축과 "되돌려 확인이 필요한지". `needs_confirm: true`면 프론트가 `[맞아요][다시 고를래요]`를 띄운다
- `profile_completion` 신규 — 뮤즈 프로필 완성도

**답변 원칙 절 갱신** — 페르소나가 안내원에서 큐레이터로 바뀐다.

```
- 정보 질문에는 정보로 먼저 답한다. 서사는 마지막 한 문장까지만
- 손님의 "선택"을 해석하고 "사람"을 단정하지 않는다
- 근거 없는 칭찬을 하지 않는다. 단서가 적으면 "아직 읽는 중"이라고 말한다
- 답은 항상 물건으로 착지시킨다. 후보 목록의 상품·번호만 사용한다
```

### 변경하지 않는 문서

- **공통 규약** — `role` 4종으로 충분(가설은 `assistant`, 응답은 `user_action`)
- **행동 이벤트 수집** — 새 이벤트 타입 불필요. 가설 적중률은 `chat_logs`로 계산한다 → `EventType` 변경 없음 = **마이그레이션 없음**
- **입장 · 상품 상세 · 리포트 · 관리자** — 변경 없음

## 11. 구현 순서

| | 작업 | 비용 |
| --- | --- | --- |
| 1 | 트리거 평가 함수 + 1군(상품 확인) | 1일 |
| 2 | `hypothesis_yes/no` 처리 + 관심 상품 집합 + 축값 함수 | 1일 |
| 3 | `맞아요` → 추천 3개 + 진열대 번호 | 1일 (기존 F7과 동일) |
| 4 | `아니에요` → 채팅 유도 + 사전 기반 축 추출 | 반나절 |
| 5 | 2군 대비 2택 | 반나절 |
| 6 | 3군 축 확인 (7조건) + lock | 반나절 |
| 7 | 4군 회피형 · 빠른 훑기 · 취향 변화 재질문 | 1일 |

**1~4가 최소 완결 단위.** 급하면 7 → 6 → 5 순으로 자른다. 3단계는 새 작업이 아니라 원래 계획의 챗봇 추천이고, 후보 선정 근거만 "현재 상품과 비슷한 것"에서 "관심 상품 집합의 공통 축"으로 바뀐다.

## 12. 기획 확인 필요

- **뮤즈 아키타입 16개 이름** (리포트 얼굴)
- 트리거 문구 톤 검수 — 특히 **4군 회피형**이 성향 판정("화려한 건 부담스러우신가요?")이 아니라 관찰 사실("눈에 안 들어오시는 것 같아요")로 읽히는지
- `맞아요` / `아니에요` 버튼 라벨
- **격차 임계 `0.25`와 shrinkage 계수 `2`는 상품 30개 들어온 뒤 실제 시나리오로 재조정** — 지금은 근거 없이 정할 수 없다
