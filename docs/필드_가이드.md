# O&O API 필드 가이드

프론트·기획이 백엔드 응답을 볼 때 참고하는 문서. **"이 값이 왜 있고 뭘 해야 하는지"** 를 적었다.
스키마 자체는 Swagger(`/api/schema/swagger-ui/`)가 진실이고, 이 문서는 그 의미를 설명한다.

최종 수정 2026-08-12 · 구현 완료: `POST /enter` · `GET /products/{id}` · `POST /admin/auth`

---

## 1. 먼저 알아야 할 식별자 3개

이 세 개를 헷갈리면 전부 꼬인다. **다른 것이다.**

| 이름 | 형태 | 수명 | 무엇 |
| --- | --- | --- | --- |
| `anonymous_uuid` | `f590c81a-cb3e-...` | **영구** (브라우저에 저장) | "이 브라우저는 같은 사람" 이라는 가명 식별자. 로그인 대신 쓴다 |
| `visit_id` | `v_72U1gcXPRkA` | **관람 1회** | 이번 방문. 리포트·분석의 단위 |
| `visit_token` | `hM0v9...`(랜덤 문자열) | 그 Visit이 살아 있는 동안 | **API 호출 열쇠.** 모든 사용자 API의 헤더에 넣는다 |

### 프론트가 저장해야 하는 것

```
localStorage: anonymous_uuid   ← 지우면 안 된다. 이탈 복구가 안 된다
메모리/세션:   visit_token, visit_id
```

`anonymous_uuid`는 **최초 입장 응답에만 들어온다.** 그때 저장하고, 이후 모든 `POST /enter` 요청의 `X-Anonymous-UUID` 헤더에 실어 보낸다. 안 보내면 서버는 매번 새 사람으로 취급한다.

### 왜 UUID와 visit_id를 나눴나
한 사람(UUID)이 여러 번 방문(Visit)할 수 있다. UUID는 코호트 분석(연령대별 취향 같은 것)에, `visit_id`는 이번 관람의 리포트에 쓴다.

## 2. 요청 헤더 규약

| 헤더 | 언제 | 값 |
| --- | --- | --- |
| `Content-Type: application/json` | 항상 | — |
| `X-Anonymous-UUID` | `POST /enter` 호출 시, 저장된 UUID가 있으면 | 저장해 둔 `anonymous_uuid` |
| `X-Visit-Token` | **`/enter`를 제외한 모든 사용자 API** | `/enter` 응답의 `visit_token` |
| `Authorization: Bearer <token>` | `/api/v1/admin/*` 전용 | `POST /admin/auth` 응답의 `access_token` |

사용자 API에는 로그인이 없다. `X-Visit-Token`이 로그인을 대신한다.

## 3. `POST /api/v1/enter` — 입장

### 요청

```json
{ "age_band": "20s", "gender": "female", "force_new": false }
```

| 필드 | 필수 | 값 | 설명 |
| --- | --- | --- | --- |
| `age_band` | ❌ | `10s` `20s` `30s` `40s` `50s+` | 연령대. 건너뛰기 허용 |
| `gender` | ❌ | `female` `male` `other` `na` | 성별. 건너뛰기 허용 |
| `force_new` | ❌ | `true`/`false` (기본 `false`) | **"새로 시작"을 눌렀을 때만** `true` |

- 둘 다 생략하고 `{}`만 보내도 정상 입장된다.
- **매장은 보내지 않는다.** 매장이 하나로 고정이라 서버가 붙인다.
- 연령대·성별은 **이어하기에서는 반영되지 않는다.** 이미 답한 사람에게 다시 묻지 않기 위해서다.

### 응답

```json
{
  "anonymous_uuid": "f590c81a-cb3e-4172-b792-917cf588e287",
  "visit_id": "v_72U1gcXPRkA",
  "visit_token": "hM0v9...",
  "store": { "store_id": "s_mcm", "name": "MCM 스토어" },
  "scenes": [
    { "scene_id": "sc_01", "no": 1, "name": "F/W 신상",
      "products": [
        { "product_id": "p_101", "no": 1, "name": "Heritage 백팩",
          "thumbnail": "/media/products/1.jpg", "price": 890000 }
      ] }
  ],
  "resumed": false
}
```

| 필드 | 항상? | 설명 |
| --- | --- | --- |
| `anonymous_uuid` | **신규 발급될 때만** | 이때 반드시 localStorage에 저장한다 |
| `visit_id` | ✅ | 이번 방문 식별자 |
| `visit_token` | ✅ | 이후 API 헤더에 넣을 값 |
| `store` | ✅ | 고정 매장 정보 |
| `scenes` | ✅ | 전시존 목록 + 각 존의 상품 (간략 정보) |
| `resumed` | ✅ | **아래 4장 참고** |
| `resumed_visit` | `resumed: true`일 때만 | 이어하기 모달에 띄울 요약 |

### `scenes`에 대해 오해하기 쉬운 것

**좌표·도면이 아니다.** "어느 전시존에 어떤 상품이 속하는지"만 알려주는 논리적 구성이다. 맵 UI는 프론트가 직접 만든다.

`no`(번호)를 함께 주는 이유는 **챗봇이 "3번 진열대 2번 상품에 있어요"처럼 번호로 안내**하기 때문이다. 화면의 번호와 챗봇이 말하는 번호가 같아야 한다.

`products`는 목록용 간략 정보(5개 필드)뿐이다. 이미지 여러 장·소재·스토리는 `GET /products/{id}`에서 받는다.

## 4. `resumed` — 가장 많이 물어보는 필드

**이번 입장이 새 Visit인지, 진행 중이던 Visit을 이어받은 것인지 알려준다.**

### 왜 있나

사용자가 **"관람 끝"을 누르지 않고** 창을 닫는 일이 흔하다. 그때 다시 들어올 때 새 Visit을 만들면:
- 아까 본 상품은 Visit A에, 지금 보는 건 Visit B에 쌓인다
- 리포트는 Visit 하나 기준이라 **반쪽짜리 분석**이 나온다
- 채팅 타임라인이 끊겨 챗봇이 문맥을 잃는다

그래서 같은 UUID로 **30분 안에** 다시 오면 그 Visit을 그대로 이어받는다.

### 값의 의미

| `resumed` | 뜻 | `visit_id` · `visit_token` |
| --- | --- | --- |
| `false` | 새 Visit을 만들었다 | 새 값 |
| `true` | 진행 중이던 Visit을 이어받았다 | **이전과 완전히 동일** |

`false`가 나오는 경우 세 가지:
1. 첫 방문 (`X-Anonymous-UUID` 없음)
2. 마지막 활동이 **30분**을 넘겨 이전 Visit이 만료됨
3. `force_new: true`로 보냈다 ("새로 시작")

### 프론트 동작

`resumed: true`를 받으면 **"이어서 볼까요? / 새로 시작"** 모달을 띄운다.

- **이어서** → 아무것도 호출하지 않는다. 서버는 이미 이어준 상태다. `GET /chat/messages?visit_id=`로 대화 타임라인만 복원한다
- **새로 시작** → `POST /enter`를 `{"force_new": true}`로 다시 호출한다

```json
"resumed_visit": { "started_at": "2026-08-12T07:07:57Z", "products_viewed": 3, "message_count": 12 }
```

모달에 "상품 3개를 보던 중이었어요"를 띄우기 위한 값이다. 이유를 보여주지 않으면 사용자가 이어할 이유를 모른다.

### 헷갈리지 말 것 — `resumed`는 "재방문"이 아니다

| | 만드나? | 무엇 |
| --- | --- | --- |
| **이어하기** (`resumed`) | ✅ | **진행 중**이던 관람을 이어받음 |
| 재방문 마이페이지 | ❌ | **끝난** 관람의 리포트 목록·누적 취향 |

끝난 리포트는 **slug 링크로만** 다시 본다. 마이페이지 성격의 화면은 만들지 않는다.

### 한계
`anonymous_uuid`는 브라우저 저장소에 있다. **시크릿 모드·저장소 삭제·다른 기기에서는 복구되지 않는다.** 안내 문구가 필요하다.

## 5. `GET /api/v1/products/{product_id}` — 상품 상세

헤더에 `X-Visit-Token` 필요.

```json
{
  "product_id": "p_101",
  "name": "Heritage 백팩",
  "images": ["/media/products/1.jpg"],
  "price": 890000,
  "attributes": { "color": "코냑", "material": "코팅 캔버스", "size": "30x40cm", "capacity": "15L" },
  "story": "1976년 뮌헨의 여행 가방에서 출발한...",
  "scene_id": "sc_01",
  "external_url": "https://...",
  "preset_answers": {
    "price": "890,000원입니다. 백팩 라인 중 엔트리 가격대예요.",
    "material": "코팅 캔버스에 레더 트리밍. 생활 방수가 되고...",
    "design_intent": "1976년 뮌헨의 여행 가방 실루엣을 현대적으로 재해석했습니다."
  }
}
```

| 필드 | 설명 |
| --- | --- |
| `attributes` | **화면 표기용** 자유 형식(색상·소재·크기·수납력). 분석에는 쓰지 않는다 |
| `external_url` | 본사 상품 페이지. 리포트의 '구매하기' 버튼이 여기로 간다 |
| `preset_answers` | **프리셋 버튼 3개의 문구.** 아래 참고 |

### `preset_answers` — LLM이 아니다

상품을 클릭하면 채팅 화면에 **가격 / 재질 / 디자인 의도** 버튼 3개가 뜬다. 이 문구는 미리 작성해 둔 것을 그대로 보여준다.

- **즉시 뜬다** (LLM 대기 없음) · **비용 0** · 브랜드가 문구를 통제한다
- 프리셋을 열어본 것도 기록한다 → `POST /chat/messages` (`type: preset_view`, `preset_key`). **어떤 정보를 궁금해했는지가 취향 신호**라서다
- 프리셋으로 안 풀리는 질문은 "채팅으로 대화하기" → `POST /chat`(LLM)

### 응답에 없는 것

**조회 기록은 이 API가 하지 않는다.** 상품을 열었다는 사실은 `POST /events`의 `product_view`로 따로 보낸다. 조회와 기록은 분리한다.

그리고 상품에는 분석용 필드가 더 있지만 **응답에 내려주지 않는다** (`llm_context`, 분류 축 8개). 프론트가 쓸 일이 없고, 챗봇 프롬프트 내용이 노출되면 안 되기 때문이다.

## 7. `POST /api/v1/admin/auth` — 관리자 로그인

사용자 API와 완전히 별개다. 사용자는 여전히 로그인하지 않는다.

```json
요청  { "email": "brand@mcm.com", "password": "..." }
응답  { "access_token": "eyJhbGci...", "expires_in": 3600, "store_ids": ["s_mcm"] }
```

이후 `Authorization: Bearer <access_token>`으로 `/admin/*`을 호출한다. `expires_in`은 초 단위(1시간)다.

## 8. 에러 형식 — 전부 동일하다

```json
{ "error": { "code": "INVALID_VISIT_TOKEN", "message": "유효하지 않거나 만료된 visit token 입니다.", "detail": null } }
```

프론트는 `error.code`로 분기하고, `error.message`를 사용자에게 보여주면 된다.

| HTTP | `code` | 언제 |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | 필드 검증 실패. `detail`에 필드별 메시지가 들어온다 |
| 401 | `INVALID_VISIT_TOKEN` | visit token **누락**·만료·위조 |
| 401 | `UNAUTHORIZED` | 관리자 인증 실패 |
| 403 | `FORBIDDEN` | 토큰은 맞지만 권한이 없음 (예: 이미 종료된 관람에 쓰기) |
| 404 | `NOT_FOUND` | 없는 상품·slug·경로 |
| 429 | `RATE_LIMITED` | 요청 과다 (챗봇 남용 방지) |
| 500 | `INTERNAL_ERROR` | 서버 오류 |

`detail`은 검증 실패처럼 항목별 설명이 있을 때만 채워진다.

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "입력값이 올바르지 않습니다.",
             "detail": { "age_band": ["\"70s\"이 유효하지 않은 선택(choice)입니다."] } } }
```

## 9. 자주 걸리는 것 4개

1. **URL 끝에 슬래시가 없다.** `/api/v1/enter` (O) / `/api/v1/enter/` (X → 404)
2. **빈 바디도 `{}`는 보내야 한다.** `Content-Type: application/json`인데 본문이 비면 파싱 에러가 난다
3. **404가 HTML로 보이는 건 정상이다.** 로컬(`DEBUG=True`)에서는 Django 디버그 페이지가 먼저 뜬다. JSON 404는 배포 환경에서만
4. **`X-Anonymous-UUID`를 안 보내면 이어하기가 안 된다.** 매번 새 사람이 된다

## 10. 앞으로 추가될 것 (구현 예정)

프론트가 미리 준비할 수 있게 계약만 적어둔다. **아직 호출하면 404다.**

| 엔드포인트 | 무엇 |
| --- | --- |
| `POST /api/v1/events` | 행동 이벤트 배치 전송 |
| `POST /api/v1/chat/messages` | 클릭을 대화 타임라인에 적립 |
| `GET /api/v1/chat/messages` | 타임라인 복원 (이어하기 직후 사용) |
| `POST /api/v1/chat` | 챗봇 (SSE 스트리밍) |
| `POST /api/v1/visits/{visit_id}/finish` | 관람 종료 → 리포트 slug 즉시 발급 |
| `GET /api/v1/reports/{slug}` | 리포트 조회 (**인증 없이** 열린다) |
| `GET /api/v1/admin/funnel` · `/admin/products` | 브랜드 대시보드 |

### 이벤트 타입 (프론트 수집기가 보낼 것)

| 묶음 | `event_type` |
| --- | --- |
| 전시존 | `scene_view` `scene_dwell` `hotspot_click` |
| 상품 | `product_view` `product_dwell` `product_save` |
| 챗봇 | `chatbot_open` `question_submit` `recommendation_impression` `recommendation_click` |

- `store_enter` · `visit_start` · `visit_end`는 **서버가 만든다.** 프론트는 보내지 않는다 (둘 다 보내면 퍼널 분모가 2배가 된다)
- `product_compare`는 **없다.** 같은 Visit에서 두 상품을 60초 안에 왕복 조회한 것을 서버가 비교로 추론한다
- `event_id`는 **클라이언트가 UUID로 생성**한다. 같은 이벤트를 두 번 보내도 서버가 걸러내므로(멱등), 실패하면 그냥 재전송하면 된다
- 체류시간은 `metadata.dwell_ms`에 담는다. 서버가 상한 5분으로 자른다(탭을 백그라운드에 두면 30분이 찍히기 때문)

### 리포트 관련 용어

| 용어 | 뜻 |
| --- | --- |
| `slug` | 리포트 주소(`r_7Ka9xQ...`). **추측 어려운 문자열이고, 이걸 아는 사람은 리포트를 볼 수 있다** |
| `status` | `pending`(분석 중) / `ready`(완료) / `failed`(실패 — 재시도 안내) |
| `payload` | 박제된 리포트 본문. 몇 번을 열어도 재계산 없이 같은 화면 |
| `confidence` | 0~1. 분석을 얼마나 신뢰할 수 있는지. **0.35 미만이면 "탐색 중"으로 표시** |
| `character_type` | 16유형 코드 4글자 (예: `CNPD`) |
| `hero` | 리포트에서 가장 크게 노출할 상품 1개 |
| `is_viewed` | 추천 상품 중 "이미 관심 있게 본 것"과 "새로 추천된 것"을 구분하는 플래그 |

리포트 `payload`에는 **상품 정보(이름·이미지·가격·구매링크)가 함께 박제된다.** 집에서 열 때는 `visit_token`이 없어서 `GET /products/{id}`를 부를 수 없기 때문이다. 리포트 화면은 payload만으로 렌더해야 한다.
