# 컨텍스트 챗봇 (AI ①)

**API Endpoint** `/api/v1/chat`
**HTTP method** `POST`
**파트** Chat
**메모** OpenAI. 상품 정보로 프롬프트 구성 → 스트리밍. 대화에서 취향·구매의도 추출

## 설명 — AI를 쓰는 첫 번째 곳

사용자가 직접 타이핑한 질문에 답한다. 진열대·상품 클릭으로 쌓인 메시지는 이 API가 아니라 `POST /chat/messages`가 기록한다.

핵심은 **문맥이 이어진다는 것**이다. "채팅으로 대화하기"로 넘어오면 그때까지 쌓인 메시지(1번 진열대 클릭 → OO 상품 클릭 → 프리셋 열람)가 지워지지 않고 남아 있고, 서버는 그걸 읽어 AI가 지금 어떤 상품 얘기를 하는 중인지 알게 한다. 그래서 사용자는 **"이 상품의 디자이너와 의도를 설명해줘"처럼 상품명을 말하지 않아도 된다.**

챗봇의 역할은 안내원이 아니라 **큐레이터**다. 손님이 말로 표현하기 어려운 감각(색·기분·분위기)을 **매장의 물건과 진열대 번호로** 짚어 준다.

## 문맥을 만드는 방법

서버가 매 요청마다 다음을 조립한다.

1. `chat_logs`에서 이번 `visit_id`의 **최근 12개** 메시지를 읽는다 (클라이언트가 다시 보낼 필요 없음)
   - 클릭 기록(`user_action`)은 `user`로, 프리셋 답변(`preset`)은 `assistant`로 매핑한다
2. 가장 최근 클릭된 진열대·상품을 현재 대상으로 잡는다
3. 그 상품의 **`llm_context` · `story` · `preset_answers` · 8개 분류 축 · 진열대·상품 번호**를 프롬프트에 넣는다
4. `age_band` / `gender`가 있으면 톤 조절에 참고한다
5. 지금까지 확정된 취향 축(`TasteProfile`)을 함께 넣는다

`context`를 명시로 보내면 그 값이 우선한다. 안 보내면 서버가 위 방식으로 알아서 잡는다.

> **`story`와 `preset_answers`를 빠뜨리면 안 된다.** `llm_context`만 넣었을 때 "디자이너 의도를 설명해줘"에 **"제공된 정보에 없습니다"** 라는 답이 나왔다. 정작 그 답이 스토리와 프리셋 문구에 있었다. 프리셋은 브랜드가 직접 작성한 문장이라 근거로 삼기에 가장 안전하다.

## 모델 / 원칙

- 모델: OpenAI `gpt-4o-mini` (`.env`의 `OPENAI_MODEL`로 교체). 키는 서버에 숨기고 `common/llm.py` 한 곳에서 모델 교체·재시도·토큰 사용량을 통제한다
- 부수 목적(중요): 대화에서 **긍정·부정 취향과 구매 의도를 추출**한다. 행동(클릭·체류)만으로는 안 드러나는 망설임을 잡는 통로이며, 추출 결과는 리포트 분석(AI ②)의 재료가 된다

### 답변 원칙

```
- 정보 질문에는 정보로 먼저 답한다. 서사는 마지막 한 문장까지만
- 손님의 "선택"을 해석하고 "사람"을 단정하지 않는다
  ("이 색을 고르셨네요" O / "당신은 이런 사람이군요" X)
- 근거 없는 칭찬을 하지 않는다. 단서가 적으면 "아직 읽는 중"이라고 말한다
- 답은 항상 물건으로 착지시킨다. 제공된 후보 목록의 상품과 진열대 번호만 사용하고,
  목록에 없는 상품이나 번호를 만들지 않는다
- 확인 가능한 상품 데이터에만 근거해 답한다. 재고·할인·입고처럼 변하는 정보는 단정하지 않는다
- 2~3문장. 손님은 매장에서 서서 읽는다
```

## 감각 표현을 축으로 바꾸는 방법

자유 발화("차분한 검정 가방", "화려한 건 싫고 오래 쓸 것")를 **8개 분류 축**으로 변환한다.

```
1차: 어휘 사전 매칭   차분한 → mood: minimal · 검정 → color: black
                     축이 3개 이상 잡히면 LLM 호출 없이 즉시 추천
2차: LLM 폴백        사전에 없는 표현("무해한", "레트로한")만 축 추출
```

사전을 먼저 쓰는 이유: **흔한 표현은 항상 같은 결과가 나오고, 비용·지연이 0**이다. 프리셋을 LLM으로 만들지 않은 것과 같은 논리다.

### 어휘 사전 (구현 위치 `apps/chat/taste_map.py`)

| 어휘 | 축 |
| --- | --- |
| 차분한 · 조용한 · 과하지 않게 | `mood: minimal` |
| 화려한 · 튀는 · 눈에 띄는 · 포인트 | `mood: bold_statement` |
| 클래식 · 기본 · 정통 | `mood: classic_heritage` |
| 힙한 · 스트리트 · 개성 있는 | `mood: y2k_street` |
| 꾸안꾸 | `mood: minimal` + `use_case: daily` |
| 오래 쓸 · 튼튼한 | `material: grained_leather` + `silhouette: structured` |
| 가벼운 | `material: nylon` |
| 비 와도 · 관리 편한 | `material: coated_canvas` |
| 출근 · 노트북 | `use_case: work` |
| 데일리 · 매일 | `use_case: daily` |
| 여행 · 짐 많이 | `use_case: travel` |
| 모임 · 나들이 | `use_case: going_out` |
| 선물 · 부담 없는 · 입문 | `price_band: entry` |
| 큰 거 · 많이 들어가는 | `category: backpack` · `tote` |
| 작은 거 · 가볍게 들 것 | `category: crossbody` · `wallet` · `accessory` |

**모호한 표현은 사전에 넣지 않는다.** 예를 들어 "무난한"은 `classic_heritage`로도 `minimal`로도 읽히는데, 사전이 한 값만 주면 틀린 추천이 나간다. 이런 표현은 **LLM 폴백으로 넘겨** 문맥을 보고 판단하게 한다.

### 부정 표현

`~는 싫어` · `~빼고` · `~말고` 가 붙으면 그 값의 **회피율에 가산**한다.

```
"화려한 건 싫어"  →  bold_statement 계열의 회피율 += 1.0
```

축값은 비율 체계이므로 음수를 직접 더할 자리가 없다. **회피율이 유일하게 스케일이 같은 자리**다(`축값 = 비율 × n/(n+2) − 회피율`). `spoken`(lock)에는 넣지 않는다 — lock은 "이것이다"를 확정하는 것이고 부정은 확정이 아니다.

추출한 축은 **되돌려 확인**한다. 단정하면 틀렸을 때 신뢰가 무너지고, 확인하면 틀려도 대화가 된다.

```
🐻 베이지 · 미니멀 · 데일리로 읽었어요.   [ 맞아요 ]  [ 다시 고를래요 ]
```

`다시 고를래요`를 누르면 **카드를 9개 나열하지 않는다.** 어긋난 축 중 우선순위 1위(`color > mood > material > pattern`) **하나만 진영 2택**으로 되묻는다.

```
🐻 색부터 다시 볼게요. 어느 쪽이 가까우세요?
   [ 차분한 색 ]   [ 눈에 띄는 색 ]
```

응답은 `POST /chat/messages`의 `type: "choice"` + `option: "color_neutral" | "color_vivid"`로 보낸다.

## Request

헤더: `X-Visit-Token` ✅ (`X-Anonymous-UUID`는 필요 없다 — `/events`만 요구한다)

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `visit_id` | string | ✅ | 대상 방문. 토큰이 가리키는 방문과 같아야 한다 |
| `message` | string | ✅ | 사용자가 타이핑한 질문. **500자 이하** |
| `context` | object | ❌ | `{ scene_id, product_id }`. 생략하면 서버가 최근 클릭 기준으로 판단. **존재하지 않는 id를 보내면 400** |

```json
{ "visit_id": "v_9f8e...", "message": "이 상품의 디자이너와 의도를 설명해줘" }
```

## Response — `text/event-stream` (SSE)

```
data: {"delta": "이 백팩은 "}
data: {"delta": "1976년 뮌헨의 여행 가방 실루엣을"}
data: {"delta": " 현대적으로 재해석한 라인입니다."}
data: {"done": true, "message_id": "m_55",
       "recommendations": [
         { "product_id": "p_204", "name": "Stark 백팩", "thumbnail": "https://.../t.jpg",
           "scene_no": 3, "product_no": 2, "reason": "선호 소재(레더)와 일치" }
       ],
       "extracted": { "axes": { "color": "beige", "mood": "minimal" },
                      "needs_confirm": true },
       "profile_completion": 0.55}
```

| 필드 | 설명 |
| --- | --- |
| `delta` | 답변 조각. 받는 즉시 이어 붙인다 |
| `done` | 스트림 종료 신호 |
| `message_id` | 저장된 답변의 id |
| `recommendations` | 추천 카드 — **아래 참고** |
| `extracted` | 이번 발화에서 뽑은 축. `needs_confirm: true`면 되돌려 확인 버튼을 띄운다 |
| `profile_completion` | 뮤즈 프로필 완성도 (0~1). **리포트의 `confidence`와 같은 값** — 계산은 한 곳뿐이고 필드명만 다르다 |

질문과 답변은 `chat_logs`에 저장되어 타임라인에 이어 붙는다(`role: user` / `assistant`).
답변은 **조각이 다 나온 뒤 한 번에 저장**한다 — 조각마다 UPDATE를 치면 스트리밍 도중 SQLite 쓰기 잠금이 걸린다.

## 챗봇 추천 — 카드 + 텍스트 병행 (확정)

A안/B안 중 택일이 아니라 **둘 다** 쓴다. 같은 추천을 두 가지로 표현한다.

| 층 | 형태 | 근거 |
| --- | --- | --- |
| 텍스트 | 답변 본문에 위치 안내 문장 — "3번 진열대 2번 상품에 있어요" | 오프라인 매장이므로 **실물을 찾아갈 수 있어야** 한다 |
| 카드 | `done` 이벤트의 `recommendations[]` | 상세로 넘어가는 클릭 경로 + 추천 클릭률 측정 |

### 후보는 서버가 고른다

```
후보 선정 (LLM 호출 전)
  1. 확정된 취향 축 + 현재 문맥 상품을 기준으로 스코어링
  2. 이번 방문에서 이미 상세를 본 상품은 제외 (새로운 발견)
  3. 상위 3개만 → 프롬프트에 name · scene_no · product_no · 핵심 축만 넣는다
```

- 프롬프트 제약: **후보 목록에 있는 상품과 번호만 언급한다.** 없는 진열대 번호를 말하면 매장에서 즉시 들통난다
- `recommendations`는 **LLM 출력이 아니라 서버가 고른 후보 그대로**다. LLM이 텍스트에서 일부만 언급했더라도 카드는 서버 기준으로 일관된다
- 카드에도 `scene_no`·`product_no`를 실어 **카드와 문장이 같은 번호**를 가리키게 한다
- 문맥 상품이 없고 축도 안 잡혔으면 `recommendations: []` — 억지 추천은 하지 않는다

어느 쪽이든 `recommendation_impression` / `recommendation_click` 이벤트는 그대로 남긴다.

## 프론트 구현 주의사항

### `EventSource`를 쓸 수 없다

`EventSource`는 **GET만** 지원한다. 이 API는 POST + `X-Visit-Token` 헤더가 필요하므로 `fetch` + `ReadableStream`으로 읽는다.

### `\n\n` 기준으로 버퍼링해야 한다

네트워크는 `data: {...}\n\n` 단위로 끊어서 주지 않는다. **한 줄이 중간에서 잘려서** 오므로 받은 덩어리를 그대로 `JSON.parse`하면 깨진다.

```js
const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
let buffer = "", answer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += value;
  const lines = buffer.split("\n\n");
  buffer = lines.pop();                    // 마지막 조각은 미완성일 수 있으니 남긴다
  for (const line of lines) {
    if (!line.startsWith("data: ")) continue;
    const p = JSON.parse(line.slice(6));
    if (p.delta) { answer += p.delta; render(answer); }
    if (p.error) { showRetry(p.error.message); return; }
    if (p.done)  { renderCards(p.recommendations); }
  }
}
```

`delta`가 잘게 쪼개지는 건 정상이다(OpenAI가 토큰 단위로 흘려보내서 "1976년"이 `197`+`6`+`년`으로 온다). 이어 붙이면 되고, 완성된 `data:` 줄을 파싱했다면 그 안의 문자열은 항상 온전하다.

## 에러

### 스트림 시작 전 — 평소의 JSON 에러

| HTTP | code | 언제 |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | `message` 누락·500자 초과 · `context`에 없는 `scene_id`/`product_id` |
| 401 | `INVALID_VISIT_TOKEN` | 토큰 누락·만료·위조 |
| 403 | `FORBIDDEN` | 토큰이 가리키는 방문이 아님 · **종료된 관람** |
| 429 | `RATE_LIMITED` | **분당 20회 초과 (방문 단위)** |

**429는 방문 단위로 센다.** IP 기준으로 세면 매장 와이파이를 함께 쓰는 손님 전체가 한 사람으로 묶여 서로의 한도를 잡아먹는다.

### 스트림 시작 후 — SSE 이벤트로 온다

이미 스트림이 시작된 뒤에는 HTTP 상태를 바꿀 수 없다. LLM 실패는 이벤트로 흘려보낸다.

```
data: {"error": {"code": "LLM_UNAVAILABLE", "message": "AI 응답을 생성할 수 없습니다. 잠시 후 다시 시도해주세요."}}
```

프론트는 그 자리에 안내 문구와 재시도 버튼을 띄운다.

### `Accept` 헤더

`accept: text/event-stream`을 보내는 클라이언트(Swagger UI, SSE 표준 방식)를 지원한다. **이 헤더를 처리하지 못하면 스트리밍 코드에 닿기도 전에 `406 Not Acceptable`이 난다.**

### LLM이 죽어도 서비스는 굴러간다

프리셋 버튼·클릭 타임라인·트리거 확인·축 기반 추천은 **LLM 없이 완결된다.** 자유 발화만 이 API를 타므로, 키가 없거나 OpenAI가 죽어도 핵심 경험이 살아 있다.
