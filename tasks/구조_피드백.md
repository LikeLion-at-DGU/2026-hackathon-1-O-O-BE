## A. 계약 위반 · 구멍 (고쳐야 함)

### A-1. 맵 API는 기획에서 확정 제외된 항목

- [ ] `stores/map_query.py` 삭제
- [ ] `api/v1/stores/` (`GET /stores/{key}/map`) 삭제

> 기획 확정 문구: 맵/평면도는 API로 받지 않고 프론트에서 직접 만든다. 좌표·도면 데이터는 내려주지 않음.

씬·상품 구성은 이미 `POST /enter`의 `scenes[]`가 내려준다. 맵 API를 따로 두면 **같은 데이터를 주는 경로가 둘**이 되고, 프론트는 어느 쪽을 믿을지 매번 물어보게 된다. 캐시 레이어까지 붙어 있어 유지 비용이 더 크다.

### A-2. `admin_users` 모델 누락

- [ ] `apps/dashboard/models.py` 추가 (`AdminUser`)

`dashboard/auth.py`(Admin JWT)는 있는데 `models.py`가 없다. `POST /admin/auth`가 email·password를 검증해야 하므로 모델이 반드시 필요하다. 명세에도 `admin_users`(신규)로 잡혀 있다.

### A-3. 채팅 액션 메시지 기록이 빠짐

- [ ] `chat/messages.py` 추가

`chat/services.py`에 `respond()`만 있다. `POST /chat/messages`(진열대·상품 클릭 → 말풍선 적립)는 **LLM을 안 타는 완전히 다른 경로**이고, 표시 문구를 서버가 생성해야 한다("1번 진열대 클릭"). `respond()`에 섞으면 안 된다.

```
chat/services.py   → respond()          # AI ①, SSE 스트리밍
chat/messages.py   → append_action()    # 문구 생성 + ChatLog 적립
                     current_context()  # 최근 클릭 scene/product
```

`current_context()`는 `respond()`와 `GET /chat/messages` 양쪽이 쓰므로 한 곳에 있어야 한다.

### A-4. 이미지 생성은 스코프 밖

- [ ] `common/imagegen.py` 삭제
- [ ] `analysis/tasks.py`의 `image_task` 삭제

기획에 이미지 생성이 없다. LLM은 ③′(취향 태그 추출)·⑦′(문장 생성) 두 곳뿐이다. 8/22 마감에 이미지 생성 큐를 붙일 여유가 없다.

## B. 덜어낼 것 (오버엔지니어링)

### B-1. 서비스 레이어가 두 층

- [ ] `api/v1/*/services.py` 전부 삭제

`apps/visits/services.py`와 `api/v1/enter/services.py`(EnterService)가 동시에 있다. "조합"이 목적이면 그건 뷰가 3~5줄로 할 일이다.

### B-2. `api/v1/`의 엔드포인트별 폴더

- [ ] views·serializers를 도메인 앱 안으로 이동
- [ ] `api/`에는 `authentication.py`, `exceptions.py`, `v1/urls.py`만 남김

8개 폴더 × 3파일 = 24파일이고 각 파일에 클래스 하나다. 그리고 이 배치는 팀 컨벤션의 프로젝트 구조(`apps/<도메인>/{serializers,views,urls}.py`)와 다르다. **1차 심사가 AI 코드 리뷰인데 관례를 벗어난 배치는 그 자체로 감점 요인.**

### B-3. `events/managers.py`의 `VisitScopedManager`

- [ ] 삭제

한 번만 쓰이는 추상화. `append_batch()`가 `Event.objects.bulk_create(..., ignore_conflicts=True)`를 부르면 끝난다.

### B-4. `visits/tasks.py`의 `close_stale_visits`

- [ ] 삭제

기획에 없다. `visit_end` 이벤트와 `/finish`가 종료를 담당하고, 안 닫힌 Visit은 `ended_at=null`로 남으면 된다. beat 스케줄러를 하나 더 띄울 이유가 없다.

### B-5. Celery는 조건부

- [ ] Redis를 띄울지 결정 → 안 띄우면 `threading.Thread` + `reports.status`로 대체
- [ ] Celery를 남기면 `CELERY_TASK_ALWAYS_EAGER` 로컬 폴백 열어두기

Redis를 이미 띄울 계획이면 그대로 가도 된다. 아니라면 `redis + worker + beat` 3개 프로세스가 **데모에서 죽을 지점만 3개** 늘린다. 계약이 요구하는 건 "`/finish`는 즉시 202, 워커가 나중에 `status: ready`"뿐이고, 스레드 + `reports.status` 컬럼으로 충족된다.

### B-6. settings 3분할 · privacy.py

- [ ] 배포를 안 하면 `settings.py` 한 파일 + env로 통합
- [ ] `privacy.py`의 `purge_expired()` 삭제, `mask_pii()`만 남김

`purge_expired()`는 지금 어느 화면에서도 호출되지 않는다. `mask_pii()`는 챗봇 로그에 실제로 필요하다.

## C. 잘 잡은 것 (건드리지 말 것)

| 항목 | 왜 맞는지 |
| --- | --- |
| **ASGI 선택** | SSE 때문에 맞다. `uvicorn`/`daphne`를 requirements에 넣고, 프록시 버퍼링 방지로 `X-Accel-Buffering: no` 헤더 추가 |
| **`api/exceptions.py` 공통 에러 포맷** | `{"error": {"code","message","detail"}}` 전 API 통일이 계약. 커스텀 핸들러가 유일한 방법 |
| **`VisitTokenAuthentication` 단일화** | 맞다. 단 `visits/services.py`의 `authenticate`와 로직이 겹치지 않게 — 토큰 검증 진실은 하나여야 한다 |
| **`pipeline.py` 순수 함수 분리** | ①~⑦이 10ms 미만 순수 연산이라는 설계와 일치. 테스트도 쉽다 |
| **`scoring.py` 상수** | 75/15/10을 `WEIGHT_PERSONAL/POPULAR/NEW`로 뽑은 것 정확. 매직 넘버 방지 |
| **`character.py` 분리** | 16유형 매핑이 결정론적이어야 한다는 요구와 일치 |
| **`common/llm.py` 게이트웨이** | 모델 교체·재시도·토큰 사용량 통제를 한 곳에서. 기획 §6과 일치 |
| **`ids.py`의 `gen_id("v")`** | `v_9f8e`, `p_101`, `r_7Ka9xQ` 형식을 한 곳에서 생성. slug는 `secrets.token_urlsafe`로 (추측 어려워야 함) |
| **`dashboard/queries.py`의 `MIN_COHORT_SIZE`** | 표본 적을 때 표시 제한. 기획 §10-5(재식별 방지·낮은 표본 명시)와 일치 |
| **도메인이 모델 소유 / api는 HTTP만** | 방향 자체는 맞다. B-2만 정리하면 된다 |

### 초안과 달라진 점만

| 초안 | 정리안 | 이유 |
| --- | --- | --- |
| `apps/identity/` | `apps/visits/`로 흡수 | `resolve_or_issue()` 하나 때문에 앱이 생겼다. Visitor·Visit은 항상 함께 쓰인다 |
| `apps/stores/` | `apps/catalog/` | Product가 가장 무거운 도메인인데 이름이 `stores`였다 |
| `stores/map_query.py` | 삭제 | 맵 API는 기획 확정 제외 (A-1) |
| `events/managers.py` | 삭제 | 한 번만 쓰이는 커스텀 매니저 (B-3) |
| `visits/tasks.py` | 삭제 | `close_stale_visits`는 기획에 없다 (B-4) |
| `common/imagegen.py` | 삭제 | 이미지 생성은 스코프 밖 (A-4) |
| `config/settings/` 3분할 | `settings.py` 1파일 | 배포 확정되면 다시 분할 (B-6) |
| `api/v1/<엔드포인트>/` 8폴더 | 각 앱의 `views.py`·`serializers.py`·`urls.py` | 24파일에 클래스 하나씩. 팀 컨벤션 구조와도 달랐다 (B-2) |
| `api/v1/*/services.py` | 삭제 | 서비스 레이어 이중화. 조합은 뷰가 3~5줄로 (B-1) |
| — | `apps/dashboard/models.py` | `AdminUser` 누락이었다 (A-2) |
| — | `apps/chat/messages.py` | 액션 메시지 기록 누락이었다 (A-3) |
| — | `catalog/fixtures/demo.json` | 시드 없으면 프론트가 첫 화면을 못 그린다 (D) |
| — | `README.md`, `.gitignore` | 심사에서 코드보다 먼저 보인다 (D) |

파일 수가 초안의 대략 절반이고, 각 앱이 `models / services / serializers / views / urls` + 도메인 로직이라는 **하나의 일관된 패턴**을 따른다. AI 리뷰어가 가장 잘 잡아내는 게 이 일관성이다.
