자세한 내용은 아래 API 명세서 표에서 각 행(기능)을 클릭하면 나옵니다. (공통 규칙·에러코드·테이블 상세도 표 안에 있음)

이게 뭐하는 서비스인지

로그인 없이 매장을 구경한 사람의 행동—뭐를 봤나, 얼마나 머물렀나, 챗봇에 뭐를 물었나를 모아둔다. 관람을 마치면 그걸 분석해서 "내 취향 리포트 + 추천 상품"을 만들어 준다. 이 데이터가 동시에 브랜드에 파는 B2B 자산이 된다.

백엔드는 DRF. 서버는 상태를 들고 있지 않고(stateless) 모든 걸 DB에서 읽는다.

전체 흐름

  1. 메인에서 입장 버튼 클릭 → 연령대·성별을 받고(건너뛰기 가능), 서버가 익명 ID를 확인(없으면 새로 발급)하고 방문(Visit) 을 만든 뒤 전시존·상품 목록을 내려준다. 매장은 하나로 고정이라 매장 지정 값은 안 보낸다. → POST /enter
  1. 진열대를 누르고 상품을 고른다. 클릭할 때마다 대화창에 메시지가 쌓인다("1번 진열대 클릭" → "OO 상품 클릭"). 상품을 누르면 가격·재질·디자인 의도 버튼이 뜨고, 미리 작성해둔 답변을 바로 보여준다(LLM 아님). → POST /chat/messages · GET /products/{id}
  1. 더 궁금하면 채팅으로 대화하기 → 쌓인 메시지를 지우지 않고 채팅으로 넘어간다. AI는 그 기록을 읽고 지금 어떤 상품 얘기인지 안다. → POST /chat
  1. 그동안의 행동(체류·횟수)은 따로 모았다가 한꺼번에 보낸다. → POST /events
  1. 관람 끝 버튼 클릭 → 서버는 "분석해줘" 작업을 대기열에 넣고 리포트 주소(slug)만 바로 돌려준다. 퇴장 설문은 없다. → POST /finish
  1. 뒤에서 워커가 분석을 끝내면 그 주소로 리포트를 본다. 집에 가서 다시 봐도 된다. → GET /reports/{slug}
  1. 브랜드는 관리자 화면에서 집계를 본다. → POST /admin/auth 로 로그인 후 GET /admin/*
🗺️ 맵/평면도는 API로 받지 않고 프론트에서 직접 만든다. 서버는 "어느 전시존에 어떤 상품이 있는지"와 상품 데이터만 준다. 좌표·도면 데이터는 내려주지 않음.

이벤트 타입이란?

사용자의 행동 하나하나가 "이벤트"다. 프론트가 이걸 모아둔 뒤 POST /events로 한번에 보낸다. 크게 4가지:

묶음언제 생기나event_type
매장/방문입장했을 때, 방문이 시작·종료될 때store_enter, visit_start, visit_end
전시존(매대)전시존을 보거나, 머물거나, 핫스팟을 누를 때scene_view, scene_dwell, hotspot_click
상품상품을 보고 머물고 찜하고 비교할 때product_view, product_dwell, product_save, product_compare
챗봇챗봇을 열고 질문하고, 추천이 뜨거나 누를 때chatbot_open, question_submit, recommendation_impression, recommendation_click

알아둘 점 두 가지:

  • 체류시간이 핵심 신호다. 메타데이터의 dwell_ms 값을 본다. 그냥 본 것보다 오래 머물거나 다시 본 상품에 더 큰 점수를 준다.
  • 같은 걸 두 번 보내도 괜찮다. event_id로 걸러 한 번만 저장한다(멱등). 네트워크가 끊겨도 재전송하면 된다.

각 이벤트의 역할

매장/방문 — 관람의 시작과 끝을 찍는다. store_enter는 퍼널 계산의 분모가 되고, visit_start/visit_end로 총 체류시간을 계산한다.

전시존 — 어느 구역이 사람을 끌어당기는지 본다. scene_view는 유입, scene_dwell은 관심 쓸림, hotspot_click은 전시존에서 상품으로 넘어간 전환이다. 진열 구성을 고치는 근거가 된다.

상품 — 취향 분석의 가장 큰 재료. 신호 세기 순서로 product_view(약함) < product_dwell(가장 중요, 오래 볼수록 관심 큼) < product_save(찜 — 의도가 명확해 가중치 높음). product_compare는 구매 직전 고민 신호이며, 브랜드엔 "자주 비교되는 조합" 데이터가 된다. 같은 상품을 다시 본 횟수도 product_view가 여러 번 쌓이는 걸로 친다.

챗봇 — 행동만으로는 안 보이는 속마음을 잡는다. question_submit은 무엇을 궁금해하는지(= 망설임 요인), recommendation_impression은 추천이 실제로 노출됐는지, recommendation_click은 그걸 눌렀는지를 재서 추천 로직 성능을 본다.

(피팅 관련 이벤트는 이번 스코프에 없음)

테이블 한줄 설명

테이블무슨 역할인지
products상품 정보. 분석용 구조화 피처(features)와 챗봇이 읽을 자연어 설명(llm_context)을 한 줄에 같이 가짐
stores매장과 그 안의 전시존 구성. 이번엔 매장 1개 고정
users익명 사용자. 이름·전화번호 같은 건 안 받고 UUID만 가짐
visits관람 1회. 입장부터 관람 끝까지의 행동을 묶는 단위. 리포트도 이 단위로 나온다
events위 행동 기록 원본. 쌓기만 하고 고치지 않음(append-only). 분석이 바뀌면 원본으로 다시 계산
chat_logs챗봇 대화 원문. 취향·구매의도를 뽑는 재료(마스킹·보존기간 대상)
taste_profiles분석 결과로 나온 사람별 취향. 취향 벡터·16유형·신뢰도(confidence)
reports완성된 리포트를 그대로 박제해 둔 것. slug로 언제 열어도 재계산 없이 같은 화면
exit_survey퇴장 설문 응답 (⚠️ 설문 채택할 때만)
원본(events)과 분석 결과(taste_profiles, reports)를 분리해 둔다. 추천 로직을 고쳐도 원본으로 재분석하면 되기 때문.

⚠️ 아직 정해야 할 것

  • 퇴장 설문(만족도 등)을 받을지 — 지금은 /finish에 선택 입력으로만 두었음
  • 연령·성별을 언제 받을지 — /finish 바디 vs 별도 화면
  • 찜 목록 화면이 필요한지 — 필요하면 GET /saves 추가
  • 챗봇 응답에 추천 상품 카드를 실을지 — recommendation_* 이벤트가 있으니 구조 확정 필요
  • "채팅 요약" 화면을 프론트가 만들지 / 백엔드가 줄지 / 리포트에 넣을지
  • 피팅은 이번엔 안 만듦 (확정)
